### 零.1 ★ v1.0.1 ~ v1.0.4 上线后的性能修复链（2026-09-16 凌晨）

**验收发现**：v1.0.0 上线后 **热态**正常（出卡 5 · 计算 2~5ms · HTTP ~300ms），
但**冷启动**（函数实例刚被唤醒，= 用户早上第一次打开）3.5~4.4s、出卡仅 1~3 张。

| 版本 | 改动 | 效果 |
|---|---|---|
| **v1.0.1** | 轻轨静态数据折进 `loadStatics` 并行窗口（`LrtPreload`，轻轨桶 0 次 DB 往返）+ 桶并发 3→12 | 轻轨桶不再恒定 1.2s 超时 |
| **v1.0.2** | 连接池 max 5→12 · 推荐路径桶内批并发 3→6 · **桶超时 1.2s→3s** · **轻轨「首班前」死代码修正** · 不足 5 张时说明原因 | **桶超时 9→0**；冷启动出卡 1~3 → **5 张** |
| **v1.0.3** | `route_stations` 改 `array_agg` 聚合（2870 行/270 KB → 119 行/26 KB，−90%） | **staticMs 纹丝不动（2283ms）** → 反证瓶颈不是传输量 |
| **v1.0.4** | 静态**原始行**放进 **Vercel Data Cache**（`unstable_cache`，跨实例 · 跨冷启动持久） | **staticMs 2283ms → 136ms** ✅ |
| **v1.0.5** | DSAT **记账改响应后补记**（`next/server` 的 `after()`；非请求上下文回退为直接调用） | 记账不再占用请求时间；**日志零丢失**（已核对：部署后触发 9 次调用 → 生产库新增 9 条） |

**★★★ 核心教训：Vercel Hobby 的函数区域**

- `export const preferredRegion = "sin1"` 在 **Hobby 下完全不生效**。判据 = 响应头
  `x-vercel-id: hkg1::iad1::…` → 函数真身在 **iad1（美东华盛顿 DC）**；改函数区域是 **Pro 特性**。
- 由此产生一个**与查询大小无关的固定成本**：函数在 iad1、主库在 ap-southeast-1（新加坡），
  每次**冷启动重建数据库连接**要 TCP + TLS + SCRAM 认证 + startup ≈ 5~6 个往返 ≈ **2.3s**。
- **这正是 v1.0.2（提高连接池上限）与 v1.0.3（传输量 −90%）双双失效的原因** ——
  它们改的是"连接数"和"数据量"，而瓶颈是"建连次数 × 单次建连成本"。
  ★ **判据**：若某项优化让"数据量降 9 成"而耗时不动，就要立刻怀疑固定成本，别再优化 SQL。
- **正解**：把**低频变更的静态数据**（站序 / 段统计 / 步行 / 换乘 / 方案腿 / 轻轨时刻表）
  放进 **Vercel Data Cache**（`unstable_cache`，`revalidate: 60`）→ 跨实例、跨冷启动持久命中。
  ⚠️ **只能缓存原始行（纯 JSON）**；索引（Map）必须每次在内存重建
  —— Map 不可 JSON 序列化，整体缓存会**静默丢成 `{}`**（极隐蔽）。
- **剩余瓶颈**：实时层 DSAT —— 函数在 iad1（美东）、DSAT 在澳门，**跨太平洋往返**吃掉了绝大部分时间。
  ⚠️ ⚠️ **2026-09-16 更正：此处原写「属物理下限」—— 这个结论是错的。**
  实测证据（`.verify/dsat-lat.mjs`，本机 = 澳门侧跑同一接口）：
  **单次仅 10~77ms、6 线端到端 19~92ms**；而线上（函数在 iad1）单桶 **1735~1946ms**。
  差 **20 倍** → **DSAT 服务端一点也不慢**，慢的是「函数被 Vercel 放在美东」这个**部署事实**。
  ★ 关键判据：请求的**边缘节点本来就是 hkg1（香港）**（`x-vercel-id: hkg1::iad1::…`）——
  把实时层挪到边缘执行就能绕开跨洲（预期 1.75s → ~60ms）。
  但 **Edge Runtime 不支持 `pg`（记账）与 `node:crypto` 的 md5（DSAT token）**，
  且需要前端改两段式加载 → 属**动架构**。用户 2026-09-16 明确选择「**先只做代码优化**」= v1.0.5，
  该方向**可行性已验证、留待将来拍板**。

**当前线上状态（v1.0.5，2026-09-16 01:00 实测）**：热态 p50 ~300ms · 静态层 133ms ·
冷启动总 ~2.9s（外部视角）· 冷启动实时层 971ms（v1.0.4 同期为 1958ms）。
⚠️ 实时层这次降幅（≈1s）**大于记账本身的成本**（预期 ~0.25s），主因很可能是网络/连接状态波动，
**不宜全部归因于 v1.0.5**；v1.0.5 的确定收益是「记账不再占用请求时间」。
用户已在澄清中明确选择「**宁可多等、也要真实数据**」（不接受估算卡），故冷启动 >2s 是**已知且接受**的代价。

**口径补充（本轮定案）**
- ★ **超时 ≠ 收班**：DSAT 桶超时仍按「无车剔除」，**不降级为估算卡**（用户明确要求卡片不含估算）；
  代价是服务器刚睡醒时卡片可能不足 5 张 → 此时页面**明确说明原因**（真实几张就几张）。
- 轻轨空态判定的正确优先级（原 `before_first` 是死代码）：
  **昨日跨午夜续班仍有车 → 今日首班前 → 今日还有后续班次 → 今日已收车**。
- ✅ **已完成（v1.0.5）**：`logDsatCall` 由 `await` 改为 `after()` 响应后补记。
  回归已核对：部署后触发新调用 → 生产库 `dsat_call_logs` 新增 **9 条（id 2913~2921）· 零丢失**。

实现：**优先级互斥组**（组内出现任一「优先站」即剔除该组全部「次要站」，按主码比较 → `C690/1`、`T363/2` 一并覆盖），
在 `boardsOf` / `alightsOf` 出参前过滤。**⚠️ 只作用于预测卡片链路**；开发者模式计时链路不经过本文件。

离线验证（**直接跑真实 `enumerate.ts`**，`.verify/verify-priority.ts`）：
- home→school：26A 由 `T363/1 + T367` 收敛为 **仅 `T367`**
- school→home：51A/51B/51 全部收敛为 **`C690/1` / `C690/2` / `C690/3`**（`C688/2` 消失）
- gate→home：25AX/51/51B 收敛为 `C690/2` / `C690/3` / `C690/2`
- 断言 ✅ 无「优先站存在却仍保留次要站」的候选
- ⚠️ **25 路本来到不了 `T367`** → 其 `T363/2` 保留（规则**不做跨线路取舍**，只处理同线多候选）

**B. 轻轨首段倒计时 → 只下发「你走得到的那几班」（`model.ts`）**

用户怀疑「显示的不是能赶上的那一班」→ **证实**。旧版把 `lv.departures` 原样交给客户端，
而 `<LrtEtaInline>` 取**第一班** → 显示的是「马上就要开、但你还在路上」那班。
实测（16:3x）：步行出门 **4.6 分**，却显示「**1.8 分**后开」，与 `waitMin 3.2 分`（按 `cursor` 之后第一班算）自相矛盾。
→ 现按 `> now + 步行分钟` 过滤后下发 ⇒ 客户端第一班 ≡ 模型采用的那一班。

**C. 巴士两辆候选 → 取到站更早的那辆（`model.ts#pickBoardable`）**

排查用户提的「两辆车只考虑了快的一班」→ **该担忧不成立**：模型本来就会依次看 `nearest` 与 `second`
（实测 26A 卡片显示「还有 3 站」＝第二辆，而 DSAT 的 nearest 是 1 站 → 确实用了第二辆）。
**但顺带查出另一个真问题**：`eta.ts` 的 `inTransit` 只按 `stopsAway` 排序、**不区分 `status`** ——
同站同站数时「已离站驶向下一站」(`status=0`，第 1 跳已算 0) 其实比「仍停靠该站」(`status=1`) **更早到**，
却可能被排在后面 → 旧 `pickBoardable` 取列表序第一个就会**选中实际更晚的那辆**。
实测样本：25 路 `AB5178`(status=1) 与 `AC3949`(status=0) 同在 `C654/3`、同为「还有 1 站」。
→ 现改为在**两辆都可能赶上**时取 `loSec` 更小者（= 到站更早）。
**⚠️ 只改推荐模型内部，不动 `eta.ts`**（那是计时/开发者模式共用的，改它会波及计时）。

**⚠️ 已知局限（本次未改）**：`eta.ts` 只取**前两辆**在途车 → 若两辆都赶不上，即使第三辆 3 分钟后到，
整条路线仍会被剔除（v1.1.1 定的口径）。是否放宽需用户拍板。

## 三、★★ 核心口径（**最容易误解的两条**）

### 3.1 「合并」= 起点站相同的路线归到同一张卡片

层级是 **卡片 → 卡内路线方案**：

- **一个 `commute_plans` 行 = 一张卡**（`RoutePlanList.tsx` 一 plan 一卡）
- **卡内「首段载具」的 `route_options` 每个条目 = 一条独立路线方案**
- **卡片分组判据 = 起点侧的候选上车站集合**（同一个候车区的站归一张卡）

> 例（主人亲口给的）：**擎天匯 → 橫琴口岸 = 3 条路线 / 2 张卡**
> 卡A（起点 `C653`）含 2 条：`26→T355/2(換乘)` · `50→T355/2(換乘)`；卡B（起点 `LRT-SPW`）1 条轻轨。

- **全库在用：14 张卡 = 29 条路线** → **盘点「路线」时禁止只数 plan 数**（14 是卡片数）
- 计时可**分别选线**（chips → `timer_sessions.route_code`）→ 卡内每条路线的耗时分别采得到

### 3.2 时间口径 = **离开口径**

打点 = 「关好门准备起步」；`t(下) − t(上)` = `run + dwell_B`。
（三口径 MAD 对照：离开 34s ＜ 到达 39s ＜ 纯行驶 63s）

**轻轨同理**：轻轨腿 = `board → station_arrive×N → alight`，**所有打点都在「关门出发瞬间」**
→ `board` 与 `station_arrive` **都算「发车」**；`alight`（下车）单列。

## 四、★ 轻轨氹仔线发车偏移（本轮最大结论）

📄 定稿：`docs/轻轨氹仔线发车偏移分析-20260915.md`

### 4.1 逐站 × 方向（有效会话，**禁止用线路级混合值**）

| 站 | 方向 | n | 中位 | 范围 |
|---|---|---|---|---|
| 科大站 | →媽閣 | 2 | +34 s | +34 ~ +76 |
| 路氹東站 | →媽閣 | 3 | +94 s | +53 ~ +98 |
| 東亞運站 | →媽閣 | 3 | +71 s | +33 ~ +74 |
| 協和醫院站 | →氹仔碼頭 | 4 | +26 s | +13 ~ +55 |
| 東亞運站 | →氹仔碼頭 | 4 | +32 s | +2 ~ +38 |
| 石排灣站 | →協和醫院 | 4 | **+2 s** | +1 ~ +18 |
| 協和醫院站 | →石排灣 | 3 | **+3 s** | +2 ~ +3 |

→ 氹仔线 **13 站仅 4 站有样本、9 站零样本**；全部为 `mon_thurs`。

### 4.2 根因锁定：**氹仔线表定「逐跳间隔」恒定 = 2.0 分钟**

反推法：同一趟车内 `表定间隔 = 实测间隔 − (偏移_后 − 偏移_前)`，**无需任何估计**。

- 5 对邻站 / 11 次测量 → 表定**全部落在 119~121 秒**
- 而实测区间 **76~139 秒（±25%）**
- 交叉验证：`last_min` 沿 →媽閣 严格 2 分/跳（氹仔碼頭 23:15 → 科大 23:19 → 路氹東 23:21 → 東亞運 23:23 → 協和醫院 23:25）

**⇒ 偏移 = 各跳误差累计 → 逐站漂移**（s181 一趟内 +76→+94→+71→+57，极差 37 s）
**🚫 因此禁止在 `src/` 加线路级常数偏移**（上一版「统一 +45~60 s」建议**已作废**）→ 须建**逐站 × 方向 × 班别**偏移表。

### 4.3 石排湾线为何能精准读秒

只有 **1 个区间** → 均匀模型无累计误差 → 实测 +1~+18 s（中位 +2~+3 s），7/7 全在 20 秒内。
★ 该读数同时是**方法自证**：若打点存在系统滞后，它也会偏。

### 4.4 横琴线

**有效样本 0**（仅 2 条测试）→ **待补**。
