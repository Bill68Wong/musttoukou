### 零.1 ★ v1.0.1 ~ v1.0.4 上线后的性能修复链（2026-09-16 凌晨）

**验收发现**：v1.0.0 上线后 **热态**正常（出卡 5 · 计算 2~5ms · HTTP ~300ms），
但**冷启动**（函数实例刚被唤醒，= 用户早上第一次打开）3.5~4.4s、出卡仅 1~3 张。

| 版本 | 改动 | 效果 |
|---|---|---|
| **v1.0.1** | 轻轨静态数据折进 `loadStatics` 并行窗口（`LrtPreload`，轻轨桶 0 次 DB 往返）+ 桶并发 3→12 | 轻轨桶不再恒定 1.2s 超时 |
| **v1.0.2** | 连接池 max 5→12 · 推荐路径桶内批并发 3→6 · **桶超时 1.2s→3s** · **轻轨「首班前」死代码修正** · 不足 5 张时说明原因 | **桶超时 9→0**；冷启动出卡 1~3 → **5 张** |
| **v1.0.3** | `route_stations` 改 `array_agg` 聚合（2870 行/270 KB → 119 行/26 KB，−90%） | **staticMs 纹丝不动（2283ms）** → 反证瓶颈不是传输量 |
| **v1.0.4** | 静态**原始行**放进 **Vercel Data Cache**（`unstable_cache`，跨实例 · 跨冷启动持久） | **staticMs 2283ms → 136ms** ✅ |
| **v1.0.5** | DSAT **记账改响应后补记**（`next/server` 的 `after()`；非请求上下文回退为直接调用） | 记账不再占用请求时间；**日志零丢失**（已核对：部署后触发 9 次调用 → 生产库新增 9 条） |

**★★★ 核心教训：Vercel Hobby 的函数区域**

- `export const preferredRegion = "sin1"` 在 **Hobby 下完全不生效**。判据 = 响应头
  `x-vercel-id: hkg1::iad1::…` → 函数真身在 **iad1（美东华盛顿 DC）**；改函数区域是 **Pro 特性**。
- 由此产生一个**与查询大小无关的固定成本**：函数在 iad1、主库在 ap-southeast-1（新加坡），
  每次**冷启动重建数据库连接**要 TCP + TLS + SCRAM 认证 + startup ≈ 5~6 个往返 ≈ **2.3s**。
- **这正是 v1.0.2（提高连接池上限）与 v1.0.3（传输量 −90%）双双失效的原因** ——
  它们改的是"连接数"和"数据量"，而瓶颈是"建连次数 × 单次建连成本"。
  ★ **判据**：若某项优化让"数据量降 9 成"而耗时不动，就要立刻怀疑固定成本，别再优化 SQL。
- **正解**：把**低频变更的静态数据**（站序 / 段统计 / 步行 / 换乘 / 方案腿 / 轻轨时刻表）
  放进 **Vercel Data Cache**（`unstable_cache`，`revalidate: 60`）→ 跨实例、跨冷启动持久命中。
  ⚠️ **只能缓存原始行（纯 JSON）**；索引（Map）必须每次在内存重建
  —— Map 不可 JSON 序列化，整体缓存会**静默丢成 `{}`**（极隐蔽）。
- **剩余瓶颈**：实时层 DSAT —— 函数在 iad1（美东）、DSAT 在澳门，**跨太平洋往返**吃掉了绝大部分时间。
  ⚠️ ⚠️ **2026-09-16 更正：此处原写「属物理下限」—— 这个结论是错的。**
  实测证据（`.verify/dsat-lat.mjs`，本机 = 澳门侧跑同一接口）：
  **单次仅 10~77ms、6 线端到端 19~92ms**；而线上（函数在 iad1）单桶 **1735~1946ms**。
  差 **20 倍** → **DSAT 服务端一点也不慢**，慢的是「函数被 Vercel 放在美东」这个**部署事实**。
  ★ 关键判据：请求的**边缘节点本来就是 hkg1（香港）**（`x-vercel-id: hkg1::iad1::…`）——
  把实时层挪到边缘执行就能绕开跨洲（预期 1.75s → ~60ms）。
  但 **Edge Runtime 不支持 `pg`（记账）与 `node:crypto` 的 md5（DSAT token）**，
  且需要前端改两段式加载 → 属**动架构**。用户 2026-09-16 明确选择「**先只做代码优化**」= v1.0.5，
  该方向**可行性已验证、留待将来拍板**。

**当前线上状态（v1.0.5，2026-09-16 01:00 实测）**：热态 p50 ~300ms · 静态层 133ms ·
冷启动总 ~2.9s（外部视角）· 冷启动实时层 971ms（v1.0.4 同期为 1958ms）。
⚠️ 实时层这次降幅（≈1s）**大于记账本身的成本**（预期 ~0.25s），主因很可能是网络/连接状态波动，
**不宜全部归因于 v1.0.5**；v1.0.5 的确定收益是「记账不再占用请求时间」。
用户已在澄清中明确选择「**宁可多等、也要真实数据**」（不接受估算卡），故冷启动 >2s 是**已知且接受**的代价。

**口径补充（本轮定案）**
- ★ **超时 ≠ 收班**：DSAT 桶超时仍按「无车剔除」，**不降级为估算卡**（用户明确要求卡片不含估算）；
  代价是服务器刚睡醒时卡片可能不足 5 张 → 此时页面**明确说明原因**（真实几张就几张）。
- 轻轨空态判定的正确优先级（原 `before_first` 是死代码）：
  **昨日跨午夜续班仍有车 → 今日首班前 → 今日还有后续班次 → 今日已收车**。
- ✅ **已完成（v1.0.5）**：`logDsatCall` 由 `await` 改为 `after()` 响应后补记。
  回归已核对：部署后触发新调用 → 生产库 `dsat_call_logs` 新增 **9 条（id 2913~2921）· 零丢失**。

实现：**优先级互斥组**（组内出现任一「优先站」即剔除该组全部「次要站」，按主码比较 → `C690/1`、`T363/2` 一并覆盖），
在 `boardsOf` / `alightsOf` 出参前过滤。**⚠️ 只作用于预测卡片链路**；开发者模式计时链路不经过本文件。

离线验证（**直接跑真实 `enumerate.ts`**，`.verify/verify-priority.ts`）：
- home→school：26A 由 `T363/1 + T367` 收敛为 **仅 `T367`**
- school→home：51A/51B/51 全部收敛为 **`C690/1` / `C690/2` / `C690/3`**（`C688/2` 消失）
- gate→home：25AX/51/51B 收敛为 `C690/2` / `C690/3` / `C690/2`
- 断言 ✅ 无「优先站存在却仍保留次要站」的候选
- ⚠️ **25 路本来到不了 `T367`** → 其 `T363/2` 保留（规则**不做跨线路取舍**，只处理同线多候选）

**B. 轻轨首段倒计时 → 只下发「你走得到的那几班」（`model.ts`）**

用户怀疑「显示的不是能赶上的那一班」→ **证实**。旧版把 `lv.departures` 原样交给客户端，
而 `<LrtEtaInline>` 取**第一班** → 显示的是「马上就要开、但你还在路上」那班。
实测（16:3x）：步行出门 **4.6 分**，却显示「**1.8 分**后开」，与 `waitMin 3.2 分`（按 `cursor` 之后第一班算）自相矛盾。
→ 现按 `> now + 步行分钟` 过滤后下发 ⇒ 客户端第一班 ≡ 模型采用的那一班。

**C. 巴士两辆候选 → 取到站更早的那辆（`model.ts#pickBoardable`）**

排查用户提的「两辆车只考虑了快的一班」→ **该担忧不成立**：模型本来就会依次看 `nearest` 与 `second`

**但顺带查出另一个真问题**：`eta.ts` 的 `inTransit` 只按 `stopsAway` 排序、**不区分 `status`** ——
同站同站数时「已离站驶向下一站」(`status=0`，第 1 跳已算 0) 其实比「仍停靠该站」(`status=1`) **更早到**，

实测样本：25 路 `AB5178`(status=1) 与 `AC3949`(status=0) 同在 `C654/3`、同为「还有 1 站」。
→ 现改为在**两辆都可能赶上**时取 `loSec` 更小者（= 到站更早）。
**⚠️ 只改推荐模型内部，不动 `eta.ts`**（那是计时/开发者模式共用的，改它会波及计时）。

**⚠️ 已知局限（本次未改）**：`eta.ts` 只取**前两辆**在途车 → 若两辆都赶不上，即使第三辆 3 分钟后到，
整条路线仍会被剔除（v1.1.1 定的口径）。是否放宽需用户拍板。

### 零.5 ★ v1.1.4（2026-09-16 傍晚）—— 巴士候选池改为「还没到上车站的全部车」

**背景**：v1.1.3 后暴露一个局限 —— 推荐只用 `nearest`/`second` **两辆**在途车，
两辆都赶不上就**整条剔除**；实测高峰期「第 3 辆 3 分钟后到」的路线被白丢。

**用户定稿口径**：「改进算法，看**还没有到上车站的所有车**」——即候选池 =
**所有还没驶过用户上车站的在途车**，**不设条数上限**。

**实现（三处，全部在推荐链路，计时/首页零影响）**

| 文件 | 改动 |
|---|---|
| `dsat/eta.ts` | ① `EtaBus` 加 **`passed?: boolean`**（`true` = 已过用户站、环线按 `N+diff` 绕圈计）→ 只在环线的「刚离站 / 已过站」两条分支置位<br>② `EtaRouteResult` 加 **`rest?: EtaBus[]`** = 第 3 辆起的**全部**在途车（`inTransit.slice(2)`，**不截断**）<br>③ **`nearest`/`second` 语义完全不变** → 计时 / 首页 `LiveEta` / `eta-smooth` 行为字节级不变 |
| `recommend/live.ts` | 候选池 = `[nearest, second, ...rest]` **过滤掉 `passed`** → 顺序沿用站距升序；`empty` 改为「**该方向没有一辆还没到站的车**」 |
| `recommend/model.ts` | `pickBoardable` 遍历 `[nearest, second, ...more]`，仍取「能赶上的里 `loSec` 最小者」（v1.1.3 口径） |

**为什么排除 `passed` 而不只是加条数上限**：环线的「绕圈车」虽理论上会回来，但往往要等**一整圈**
（实测可达 40 分钟）。把它们算作「可赶上」会让「赶不上就整条剔除」**名存实亡**（环线永远有车）。

**代价与收益**
- ✅ 语义最干净：无「2 辆 / 5 辆」这类魔法数字
- ✅ **零额外 DSAT 请求**（原始响应本来就返回全部在途车，实测单线单方向最多 23 辆）
- ✅ **纯增益**：`service.ts` = `sortCards(cards).slice(0, 5)`、`sortCards` 按 `totalMin` 升序
  → 候选变多**不会挤掉更优的方案**（只会排到后面：填空位或不显示）
- ⚠️ `missed`（「N 条路线赶不上首班车」）出现频率会下降 —— 因为能兜底的车变多了（符合预期）
- ⚠️ `empty` 语义变化：只有「**该方向一辆还没到站的车都没有**」才整条排除

**⚠️ 教训（已写进 MEMORY）**：2026-09-16 我曾断言「放宽会让更多路线挤掉更优方案」—— **错**。
凡「加候选会挤掉好方案」的说法，先回来看 `service.ts` 那两行排序/截断。

### 零.6 ★ v1.1.5（2026-09-16 傍晚）—— 卡内列出「后续班次」

**背景**：v1.1.4 放宽候选池后暴露一个 UX 缺口 —— 卡片只展示「能赶上的里**最早到**」那一辆，
所以当它**要求冲刺**（档 1~2）时，后面「**正常走就能赶上**」的车**完全不显示**
→ 不想跑的用户以为这条线没戏，转去选慢得多的方案。
实测（2026-09-16）：9 张卡里 **3 张是档 1**；**home→關閘 整个方向只有 1 张卡且恰是档 1** → 用户「不想跑」时无路可选。

**用户定稿口径**
> 「在**那张卡里面**把第二辆加上。但如果第二辆还有很久到就没有意义 →
>  限制：做这一班车的话，**门到门总时长要不差于五张卡片方案中的第五**；
>  并且**不止列后面一班，应列出后面所有**满足该条件的车；车的右边也要标注**怎样能赶上的分档**。」

**实现（4 处）**

| 文件 | 改动 |
|---|---|
| `recommend/types.ts` | 新增 `AltBusView`（`stopsAway` / `waitText` / `tier` / `tierText` / `totalMin`）；`RecommendCard` 加 `altBuses?` |
| `recommend/model.ts` | `modelOption` 返回值改为 **`ModeledOption { card, alts }`**；新增 `busPool` / `chosenBus`；末尾用 `restMs = cursor − boardAtMs` 给每辆后车算「若乘它」的门到门总时长与档位（**赶不上的不列**），按总时长升序 |
| `recommend/service.ts` | 排序取前 N **之后**才回填：阈值 = **第 N 张卡的总时长**，只保留 `alt.totalMin ≤ 阈值` 的（`modelOption` 无法预知阈值，故必须在此处做） |
| `components/RecommendCard.tsx` + `globals.css` | 首段等车行下方渲染后续班次列表（每行 = 还有 N 站 · 約 X~Y 分 + 右侧档位徽章），新增 `.rc-alts` / `.rc-alt` 样式 |

**性质**
- ✅ **不另开卡**：仍是一张卡，只是卡内多几行 —— 不占 5 个名额
- ✅ **自限幅**：第 5 张卡自己的后车必然超阈值 → 天然被滤掉；排在前面的卡才可能带后车
- ⚠️ **近似**：多段路线里第 2 段起的等车按**本班**的到达时刻定 —— 巴士第 2 段恒用「班距 ÷ 2」估（与本班无关，精确）；
  轻轨第 2 段取「到达后第一班」→ 换更晚的首段车时可能赶上更晚的一班，该 `alt` 的总时长**略偏乐观**。
  该字段只用于「值不值得列出来」的展示筛选，**不参与排序与主数字**，故接受此近似。

### 零.9 ★ v1.1.10（2026-09-17）—— Supabase 安全加固 + 口令门改分级保护

**起因**：Supabase 提示「RLS Disabled in Public」。复核时**发现两件独立的暴露**，第二件更严重。

#### 🔴 暴露一：数据库层（告警说的这条）

实测复核（只读 + 事务内实验，零副作用）：

| 项 | 实测结果 |
|---|---|
| public 下的表 | **21 张，RLS 全关** |
| `anon` / `authenticated` 的授权 | **每张表都有 SELECT/INSERT/UPDATE/DELETE/TRUNCATE**（合计 294 项） |
| `SET LOCAL ROLE anon` 实测 | 读到 `timer_sessions` **250 行**、`ride_crowd` 48 行，且 DELETE 通过权限检查 |
| PostgREST 裸访问 | `401 No API key found` ⇒ 需要 anon key |
| 默认授权（`pg_default_acl`） | `postgres · public · r → {..., anon=arwdDxtm, authenticated=arwdDxtm}` ⇒ **新建表会自动裸露** |

⇒ 只要 anon key 泄露（Supabase 本就把它当公开信息），**绕过应用直连即可读写删全库**。

#### 🔴🔴 暴露二（更严重）：应用层 —— 口令门形同虚设

实测线上：
```
GET  /recommend        → HTTP 200，直接返回推荐页（不是登录页）
POST /api/timer {空}   → HTTP 400「缺少 planId」   ← 请求跑到了业务层，说明守卫没拦
```
根因：`middleware.ts` 里 `ACCESS_PASSWORD` **未在 Vercel 配置** → `if (!password) return NextResponse.next()`
⇒ **守卫整体失效，全站（含数据页、导出 CSV、建计时会话）对全网敞开**。

#### ✅ 修复（用户口径：「网站是给别人用的要公开，但开发者模式只有我能开、数据只有我能看」）

**① 口令门改为「分级保护 + 默认拒绝」（`src/middleware.ts` 重写）**

- **公开**（精确白名单）：`/` `/recommend` `/card` `/about` `/login` + `/api/auth` `/api/recommend` `/api/card` + `/_next`
- **要口令**（其余全部，**默认拒绝** ⇒ 以后新增页面不会因忘记加名单而裸露）：
  `/routes` `/records` `/stats` `/free*` `/timer*` `/finish*` + 它们全部接口（含 `/api/export`、`/api/plan s`）
- `/api/cron/rebuild` 由自身 Bearer 鉴权，不受口令门约束
- ⚠️ **fail-closed**：`ACCESS_PASSWORD` 未配置时**生产环境也拒绝**受保护区（开发环境放行）
  —— 即使忘了配环境变量，也不会把数据敞开

**② RLS 开 + 收钥匙（`db/migrate-v1110-rls.ts`，已执行）**

- 给 public **21 张表全部开启 RLS**（**不加策略** → 默认全员看不见）
- **收回** `anon`/`authenticated` 的表 / 序列 / 函数权限（294 项 → **0 项**）
- **改默认授权**：`ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ... FROM anon, authenticated`
  ⇒ 以后新建的表不再自动裸露
- `service_role` 的授权**保留**（Supabase 服务端工具链可能用到）

**③ 开发者入口只对已登录者渲染（新增 `src/lib/auth-server.ts#isAuthed`）**

- 首页：`記錄 / 統計 / 自由記站` 按钮 + `開發者模式` 开关 → 仅已登录时渲染
- 推荐页：`開發者模式` 开关 + `查看全部路線` → 仅已登录时渲染；`devMode` 与 `authed` 取 AND
- 详情页：`開始計時` 按钮 → `devMode && authed` 才渲染
- 理由：开发者模式本身只是 `localStorage` 开关、**任何人都能点开**；真正的保护是口令门的 401。
  藏起来是为了让公众看不到「点进去撞墙」的死链，同时满足用户「开发者模式只有我能开」

#### ★★ 为什么开 RLS 不会弄坏应用（已实测）

应用用 `postgres` 身份连库，该角色 **`rolbypassrls = true`** 且是全部表的属主
⇒ **绕过 RLS**。实验证据：

| 角色 | 开 RLS 前 | 开 RLS 后 |
|---|---|---|
| `anon` | 读 `ride_crowd` **48 行** | 读 **0 行**（被过滤） |
| `postgres`（应用） | 48 行 | **48 行（不受影响）** |

迁移后复验：`anon` 访问任何表 → `permission denied for table ...` ✅ ；
`postgres` 读取 `timer_sessions` 250 / `routes` 95 / `segment_stats` 460 / `walk_times` 19 行 ✅ 正常。

#### ⚠️ 用户待办（部署后必须做）

**在 Vercel 配 `ACCESS_PASSWORD` 环境变量**（Settings → Environment Variables → Production），否则受保护区会 fail-closed 锁住（公开浏览不受影响）。

### 零.10 ★ v1.1.11（2026-09-17）—— 开发者模式的正确语义：**开关始终可见，开启才要口令**

**用户澄清**：「我的意思是开启开发者模式才需要密钥，但是现在开发者模式的按钮都没了」

- `HomeClient` 的数据入口（記錄/統計/自由記站）改按 `devMode` 显示（不再按 `authed`）
- `RecommendClient` 的开关改为共用 `<DevModeToggle>`，与首页行为一致
- `/login` 页补一行说明「開發者模式與數據頁需要口令」

⚠️ **真正的安全边界仍是 `middleware.ts` 的口令门**（受保护区 401 / 跳登录）；
  开关只决定 UI 里显示哪些开发者入口，不是安全边界。

### 零.11 ★ v1.1.12（2026-09-17）—— 登录页改服务端直出（去掉 Suspense 空白首屏）

**发现**：`app/login/page.tsx` 用 `<Suspense>` 包着 `LoginForm`，而表单内部调了

  （否则 `?from=//evil.com` 会被当成跳转钓鱼的载体）

## 三、★★ 核心口径（**最容易误解的两条**）

### 3.1 「合并」= 起点站相同的路线归到同一张卡片

层级是 **卡片 → 卡内路线方案**：

- **一个 `commute_plans` 行 = 一张卡**（`RoutePlanList.tsx` 一 plan 一卡）
- **卡内「首段载具」的 `route_options` 每个条目 = 一条独立路线方案**
- **卡片分组判据 = 起点侧的候选上车站集合**（同一个候车区的站归一张卡）

> 例（主人亲口给的）：**擎天匯 → 橫琴口岸 = 3 条路线 / 2 张卡**
> 卡A（起点 `C653`）含 2 条：`26→T355/2(換乘)` · `50→T355/2(換乘)`；卡B（起点 `LRT-SPW`）1 条轻轨。

- **全库在用：14 张卡 = 29 条路线** → **盘点「路线」时禁止只数 plan 数**（14 是卡片数）
- 计时可**分别选线**（chips → `timer_sessions.route_code`）→ 卡内每条路线的耗时分别采得到

### 3.2 时间口径 = **离开口径**

打点 = 「关好门准备起步」；`t(下) − t(上)` = `run + dwell_B`。
（三口径 MAD 对照：离开 34s ＜ 到达 39s ＜ 纯行驶 63s）

**轻轨同理**：轻轨腿 = `board → station_arrive×N → alight`，**所有打点都在「关门出发瞬间」**
→ `board` 与 `station_arrive` **都算「发车」**；`alight`（下车）单列。
