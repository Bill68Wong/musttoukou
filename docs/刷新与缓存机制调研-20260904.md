# 刷新与缓存时间机制调研

> 调研日期：2026-09-04
> 范围：LiveEta 手动刷新 / 打点刷新 / 服务端 10s 缓存 / Vercel 多实例 / force 直查 / 风控 / DSAT 端数据粒度 / 与官网(motransportinfo)时间基准差异
> 结论先行：**系统存在"打点/手动刷新命中 10s 缓存返回旧值、与 force 直查快照不一致"的竞态窗口 + Vercel 多实例缓存隔离导致数值横跳**；官网实时站距滞后 5~15 分钟（14 分钟纹丝不动实测），不能作为实时对照基准——DSAT bis 为实时源。

---

## 1. 全链路时间机制现状

| 环节 | 机制 | 时效 |
|---|---|---|
| DSAT bis（官方源） | token 每分钟有效；routestation/bus 车辆数据 | 车辆挂载站切换分钟级（站间行驶 2~5 分钟），单帧数据约 10~30s 内有效 |
| 我的服务端 queryEta | `globalThis.__etaCache` Map，TTL **10s**；键 = `站\|线路组\|dir\|dest` | force=false 命中返回缓存（旧 0~10s） |
| Vercel serverless | **每实例独立 globalThis**，缓存不跨实例共享 | 同键不同实例缓存龄不同 → 刷新落不同实例数值可能横跳 0~10s |
| GET /api/dsat/eta | force 参数默认 **false**；LiveEta 前端从不带 force | 全部命中缓存 |
| auto-snapshot POST | `queryEta(..., force=true)` 绕过缓存直查并**回写缓存** | 打点时刻为最新 |
| LiveEta 手动刷新 | 前端 guard ≥10s 才放行；不带 force | 与服务端 10s 缓存叠加 → 用户两次有效点按间仍可能拿旧值 |
| 打点后刷新 | postEvent 成功 → setEtaTick → refreshKey → fetchEta（**也不带 force**） | 打点瞬间 GET 与 auto-snapshot POST 并行 → 竞态 |
| 风控 | 日限 500 次(GMT+8) / 熔断 3 连败 + 30min / 全量记账 dsat_call_logs | 本地今日实测 333 次 0 失败 |

## 2. 已定位的相容性问题

### 2.1 打点竞态：界面显示 ≠ 快照记录（主人"刷新后站距不对"的主因候选）
打点成功瞬间同时发生：
- `postEvent` → `setEtaTick` → LiveEta `fetchEta()` → GET（**force=false**）
- `auto-snapshot` POST → `queryEta(force=true)` 直查 DSAT 并回写缓存

时序竞争下 GET 可能先命中**旧缓存**（旧 0~10s 的车辆位置），而 POST 记的是**直查新值** → 界面"还有 N 站"与系统快照值不一致（差 1~3 站），且用户再手动刷新仍可能命中旧缓存 → 体感"刷新了却不对/越刷越乱"。

### 2.2 手动刷新双重节流叠加
前端 ≥10s 下限 + 服务端 10s 缓存 → 用户刷新的真实意图（拿到最新）被缓存打折；且 Vercel 多实例下缓存龄不单调（A 实例 1s 前、B 实例 9s 前），**同键数值可在实例间横跳**。

### 2.3 force 直查频率 vs 风控
若把手动/打点刷新全部改 force，每次刷新 = 每线路 1 次 DSAT 调用（3 线 = 3 次）。按 10s 一次刷新 × 10 分钟 = 60 次/线组，与日限 500 需平衡（见修复建议降频策略）。

### 2.4 官网(motransportinfo)时间基准（对照结论）
实测（2026-09-04 13:33~13:47，14 分钟）：官网 getStopInfo 的 26/51A/36/AP1/MT1 remaining **全部纹丝不动**（HE04=5.5 / HE05=22.5 / HE124=2 …）；同期 DSAT bis 同车队 HE04 从 T356/1(idx27) 持续前进至 T358(idx28)、再过站 → **官网实时站距缓存陈旧约 5~15 分钟**（其前端 15s 轮询是撞服务端慢快照）。官网静态线路/站点信息准确（用户确认），但实时站距不可作为逐帧对照基准。

## 3. 修复建议（供拍板，未实施）

1. **打点后界面刷新带 force 并与 auto-snapshot 合并**：打点成功改用 auto-snapshot 的返回值（nearestStopsAway）直接驱动界面，消除 GET/POST 双查竞态（同一 force 结果既落库又上屏）。
2. **手动刷新带 force=1**：前端 10s 下限已防抖，服务端不再二次节流；每次手动 = 至多 3 次 DSAT 调用（3 线），单用户日常 10 次内/天，远低于日限。
3. **服务端缓存 TTL 10s → 5s**，并在响应带 `cachedAgoMs`，前端"更新于 Xs 前"透明化；多实例横跳影响减半。
4. **风控审计**：force 直查计入 dsat_call_logs purpose='poll'，可日后按 purpose 细分日限（timer_grab 打点高优先、poll 刷新可放宽）。
5. （对照结论）不对齐官网口径——DSAT 官方语义（2026-09-03 实测定论）为基准。
