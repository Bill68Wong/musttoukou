# 时间口径核查报告（2026-09-13）

> 对象：`timer_events`（手动打点）与 `segment_stats`（由打点重算出的站间时长）
> 问题：打点时刻到底代表「车到站」还是「车离站」？
> 核查方式：**只读**查库（生产 Supabase），未修改任何代码或数据。

---

## 0. 结论先行

| 项 | 裁决 |
|---|---|
| 打点时刻的真实含义 | **「关好门、准备起步」= 离开口径**（车辆离开某站的时刻） |
| `src/lib/rebuild/segment-stats.ts` 第 22~25 行注释 | ❌ **错误**（写作「到达口径」），待修正 |
| 由此产生的数值影响 | **很小但不为零**：两口径差 = `dwell_A − dwell_B`，实测 **均值 −4.2 秒、σ 20.6 秒、绝对值最大 40 秒** |
| 历史 170 个段样本是否报废 | **不需要报废**，但**不确定性应被记录**（见 §5） |
| 是否阻塞自动采集开工 | **不阻塞**。追踪器原始帧同时含停靠与离站两种状态，两种口径都能事后算 |

一句话：**注释写反了，数据本身是可用的，差额只有几十秒量级且均值为零；真正要修的是「口径标签」而不是「数据」。**

## 1. 争议从哪来

`src/lib/rebuild/segment-stats.ts` 的注释把段时长定义为「到达口径」：

```
端点口径（v0.22.0）：
 · board   —— 上车时刻（= 上车站发车时刻）
 · alight  —— 下车时刻（= 下车站到达时刻）
段时长 = t(下一站) − t(上一站)，差里只含**起点站**的停站时间
```

但两条腿自相矛盾：

- 注释把 `board` 明确解释成「**上车站发车时刻**」→ 这是**离开**语义；
- 紧接着又说段时长只含「起点站停站」→ 这是**到达**语义（`dwell_A + run`）；
- 若端点真的是离开时刻，段时长应是 `run + dwell_B`。

同时，用户对自己手动打点的描述是：

> 「我之前真实实测的不论是轻轨还是巴士数据，都是记的**关门时间**。因此，自动采集 A-B 站时长也是算**离开 A − 离开 B** 的时间。」

用户是唯一的数据生产者，其亲述是**第一手权威证据**。

---

## 2. 证据一：打点瞬间的车辆快照（数据侧铁证）

`bus_snapshots` 在每次打点瞬间抓了目标线路全线的实时状态（含 `status`：`'1'` 停靠 / `'0'` 已离站）。核查会话 **#128（25 路 dir=0，车牌 AB4969，2026-09-05）**：

| 打点阶段 | 时刻 | 参照站 | 目标车 status | speed | stops_away |
|---|---|---|---|---|---|
| `depart` | 13:02:12 | C653（家） | — | — | — |
| `wait_start` | 13:04:34 | C653 | 1（停靠） | 3 | 1 |
| **`board`** | **13:07:17** | **C653** | **1（停靠）** | **3** | **0** |
| `alight` | 14:00:29 | M1/13 | 1（停靠） | 0 | 29 |

**读法**：`board` 那一刻，目标车 `status='1'`（挂在站台上）、`speed=3` km/h（≈静止/刚起步）、`stops_away=0`（距参照站 0 站）。
→ **打点发生在车辆仍停在站台的瞬间**，排除了「车已开走才补打」的可能。
→ 结合用户亲述（那一刻正在关门起步），打点 = **停站窗口的最后一瞬 = 离开时刻**。

> ⚠️ 顺带发现：`bus_snapshots` 抓的是**全线所有车**（会话 #128 一次打点写了 29 条），
> 不是只抓目标车；`stops_away` 存在**负值**（−1 ~ −19），对应「已越过参照站或反向行驶」的车。
> 下游按 `stops_away` 过滤时必须带符号处理。

## 3. 证据二：两口径的差额只有几十秒

设车辆在 A 站停站 `dwell_A`、在 B 站停站 `dwell_B`、A→B 纯行驶 `run`：

```
到达口径  t(到 B) − t(到 A) = dwell_A + run
离开口径  t(离 B) − t(离 A) = run + dwell_B
                       差额 = dwell_A − dwell_B
```

同一辆车在 **相邻两站的停站时长几乎同分布**（都是「上下客 + 等红绿灯」，无系统差异），
所以差额的**期望为 0**，只有抖动。本项目已有的双口径实测（2026-09-13 追踪实验一，
26/25 路 10 分钟、58 对同段样本）：

| 指标 | 实测值 |
|---|---|
| 均值差 | **−4.2 秒**（≈0，抵消成立） |
| 标准差 | **20.6 秒**（抖动抵消不掉） |
| 绝对值最大 | **40 秒** |

停站时长本身的实测分布（追踪器）：实验一 76 观测 **均值 44 秒 / 中位 40 秒 / 最大 363 秒（总站待发）**；
实验二 12 观测 **中位 30 秒**（晚间低谷）。→ 与上式量级自洽。

**结论**：口径搞反造成的偏差是「几十秒级别、均值为零」的噪声，
而站间时长的典型量级是 **90~190 秒**（本次核查的站→站间隔 p50 = **130 秒**）。
即：口径错误带来的相对误差约 **±10~15%**，**不足以让数据失效，但足以让 ETA 预测多飘半分钟**。

## 4. 数据侧其他观察（本次核查顺带得到）

**真实会话 57 个，有效事件 319 条**：

| 事件类型 | 条数 | 事件类型 | 条数 |
|---|---|---|---|
| `station_arrive` | 115 | `station_pass` | 18 |
| `wait_start` | 46 | `border_start` / `border_end` | 11 / 11 |
| `board` | 45 | `station_skip` | 3 |
| `alight` | 41 | `pause` / `resume` | 1 / 1 |
| `depart` | 34 | `arrive` | 24 |

会话 #128 的站→站间隔（18 对）：**min 63 秒 / p50 130 秒 / max 260 秒**；
`board → station_arrive(下一站)` = 135 秒，与该 (25路 C653→C692) 的历史真值 2.1 分（126 秒）吻合。

> **`station_pass` 的存在很重要**：它证明乘客观测到「车没停直接路过」的时刻。
> 若打点是到达口径，`pass` 的时刻应是「车经过站台的瞬间」；若是离开口径，则应是「车驶离站台的瞬间」。
> 两者在 `pass` 场景下几乎没有区别（车没停 = 到达与离开是同一瞬间），
> **所以 `pass` 事件天然不区分口径** —— 这也是为什么这个 bug 能潜伏这么久。

## 5. 影响面与处置建议

### 5.1 影响面

| 受影响对象 | 影响 | 处置 |
|---|---|---|
| `segment_stats` 现有 376 行 / 170 段样本 | 数值偏差 ±几十秒（均值为零） | **保留**，不重算（重算也无从下手：原始打点无法反推另一口径） |
| `walk_times`（步行） | **不受影响**（步行是「打点相减」，与车辆口径无关） | — |
| 未来 ETA 预测（建模 #5） | 站数→分钟累加时会被这几十秒噪声稀释 | 采样积累后可由追踪器**替换/校正** |
| 追踪器新数据 | **不受影响**（原始帧两口径都能算） | 派生时**两个口径都输出**，等定案后取其一 |

### 5.2 处置（分三步，本阶段只做第①步）

1. **【本次】只出报告，不动 `src/`** —— 用户明确要求「分析类请求不擅自改代码」。
2. **【下一轮】口径定案** —— 用追踪器数据与手动打点**在同一物理段上做双口径拟合**，
   取残差小者作为权威口径。需要至少一轮 30 分钟正式采集落盘（已有 `--truth` 对照通路）。
3. **【定案后单独发版】**
   - 修正 `segment-stats.ts` 注释（把「到达口径」改为「离开口径」，并写清与 `dwell` 的关系）；
   - 给 `segment_stats` 增加口径**来源标签**（如 `caliber` 列：`manual_depart` / `track_arrive` / `track_depart`），
     避免不同口径的行被无差别聚合；
   - 评估是否需要用追踪数据**给历史段做贝叶斯校正**。

### 5.3 为什么不阻塞自动采集

追踪器落盘的是**原始帧**（`status='1'` 停靠 / `status='0'` 已离站 + 时间戳），
到达/离开两种口径都能在派生阶段算出来。
→ **口径定案只需改派生脚本的输出标签，不需要重新采集。**
