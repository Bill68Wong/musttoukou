## 审查结论（TL;DR）

- **总体判断：需重大修订**（不是重新设计）。技术路线（本地图搜索 + 三段式计时 + 高德步行几何）方向正确、且**比设计自己描述的更可行**（见 P0-3：车程覆盖其实是 89% 不是 3.8%）；但**三处会「真的崩」的地方**必须先解决：**实时步行链路的规模/并发/架构冲突**、**短距离高德步行度量失真且设计的自检手段抓不到**、**基于过期覆盖率做的产品决策（Q2）**。
- **发现的问题：P0（阻塞）3 个 · P1（严重）8 个 · P2（建议）6 个**。
- **最致命的一条**：设计把「高德步行 distance ÷ 84」当成与实测同口径的**可靠输入**用在**首末段（典型 50~300m，正是高德的失效区间）**，而实测显示该区间高德步行距离可偏大 **6~12 倍**、且设计唯一提出的自检（`snap > 100m`）对全部异常样本**零命中** —— 这会让「赶得上」被算成「赶不上」，直接把最优方案从 5 张卡里删掉。

> 先说好的：候选走**本地 `route_stations` 图搜索（0 配额、站码天然对齐）**、车程走 **`segment_stats` + 6 级回退链**、步行只取高德的**几何距离**而非 `duration` —— 这三条选型是对的，且 `lookupHop` / `catch-up` 的复用判断准确。问题不在选型，在**实现方式与规模控制**。

## 逐角度详述

### 角度 1 · 三个危险假设的验证结果

设计附录自评了三个假设。我读完后认为**其中两个是真危险、但方向反了/漏了更狠的**，第三个（配额）排在其次。

**假设 1「本地图搜索可复现高德覆盖」—— 真危险，验证方法可执行。**
- 我实测了图本身：`route_stations` = **2870 行 / 95 线 / 119 方向 / 610 站**，主码归一去重后**有向邻接对 996 个**（`.verify/qa-review-probe.out.txt` §4）。图是齐的，风险不在「行数」，在**站序语义**：循环线（首尾同码）、站台拆分、方向推导。
- **可执行验证（不必等全功能）**：写一个离线脚本，对 N 组 OD 跑「图搜索候选」与「高德 `transit/integrated` + `AlternativeRoute=10`」做 diff，统计「我们漏了高德能给的线」的比率。这是【零新增架构】的：`enumerate.ts#segmentsOf/idxsOf/deriveDirInMemory` 已是纯函数，`高德 transit` 走 LBS 配额（150k/月，充裕）。

**假设 2「高德 distance ÷ 84 同口径」—— 真危险，且我**已经实测部分证伪**。**
- 见 P0-2 与角度 2。结论：**短距离根本不同口径**（6~12×），**中长距离也非稳定**（实测 ratio 中位 0.90、区间 [0.24, 2.82]）。这条假设是**最危险的**，架构师判断正确。
- **可执行验证（已做一部分）**：用 `walk_times` × `station_walk_distance` 对拍 + 随机 OD 高德实测（本次 8 组）。**建议把「ratio 分布」纳入 CI 体检**。

**假设 3「搜索配额压到 ~1350/月」—— 危险，但可控。**
- 见 P1-3。核心暴露点：**「本地命中 >90%」这一条没验证**。可执行验证：取近 30 天真实搜索词（或人工 200 词样本）跑本地别名库，测**真实命中率**，再回代 §A.5 模型。

**架构师漏掉的更狠假设（我的补充）**：
- ★ **「首末步行的调用量在高德 QPS/延迟下可承受」** —— 架构师完全没评估。实测站点密度 57~102/1.2km 直接把它证伪（P0-1）。**这是最可能「上线即崩」的一条，却不在自评里。**
- ★ **「`client.ts` 的硬规则①允许被实时链路 import」** —— 见 P0-4/角度 6。架构师把 `walkRouteGcj` 描述成「扩展（不改协议）」，但规则①是**禁止实时调用整个模块**，不是禁止某个函数。

### 角度 2 · 数据口径一致性（★ 最可能出问题的地方）

**① 「高德 distance ÷ 84 = 我们既有 walk_times 同口径」不成立。**
- 实测对拍（`walk_times` × `station_walk_distance`，44 组，`.verify/qa-review-probe.out.txt` §12）：**实测min ÷ (高德m÷84) 中位 = 0.90，区间 [0.24, 2.82]**，隐含速度中位 **1.58 m/s**（基准 1.40）；**24/44 实测远比高德快（ratio<0.9）**。
- 其中 zone 一致的干净样本（家/关闸侧）反而接近 1（中位 ~0.96），说明**误差不是常数、是结构性的**（与起终点类型、是否建筑内、远近强相关）→ **不能用一个系数校正**。
- 更关键：**高德自己的 `duration` 隐含恒定速度 1.25 m/s**（本次 8 组全部 `distance/duration=1.25`），而我们用 1.40 去除 → 得出的分钟会**比高德页面显示的时间短约 11%**，用户对照会产生「对不上」的信任问题。

**② 系统偏差的方向 = 压档，且落在最要命的区间。**
- 实测：直线 20~57m 的三组，高德距离偏大 **6~12×**；而「任意 POI → 最近站」的首末段**典型就是 50~300m**。
- 传导链（`catch-up.ts:34-54`）：`baseMin` 偏大 → `requiredSec(baseMin, tier)` 偏大 → `pickCatchTier` 返回更低档或 `null` → 首段赶不上 → **`ctx.missed` 整条剔除**（`model.ts:326-331`）。**最优方案会消失**，而不是「稍微不准」。
- **设计的检测手段无效**：设计 §C.4 只提「`snap > 100m` → 标估算」。实测 8 组 snap 全为 **5~7m**；`地点站点距离-核对表` 里 37 组体检样本 snap 中位 **27m、最大 44m**，7 组「绕路系数异常」样本 snap 也全部 <50m（17/7、7/36、7/23、27/7、32/4、32/7、32/14）——**snap>100m 这条规则零命中**。

**③ 三段直接相加的误差累加：不是「双重计数」，但会叠加异质误差。**
- 严格说，步行（几何）与车程（DSAT 实测）是**不同物理段**，相加合理。
- 但**换乘步行**用「高德 walking 现值」、**首末步行**也用高德，而**车程**用 DSAT → 一条 2 换乘方案里会**混入 3 个高德步行段**，每段都可能带 6~12× 的短距失真 → 误差在总时长上**累加**。设计把这些段都当「单一来源 = 高德」，未评估累加。

**④ `WalkResolver` 接缝的副作用。**
- 同一 App 内，旧 auto-line 的步行来自 `walk_times`（实测），新导航来自高德现算 → **同一段路两个数**。设计只在 §C.2 要求「标来源」，但**没有一致化策略**（旧卡与新卡对同一「家→站」可能显示不同步行分钟）→ 用户/开发者困惑。
- **降级路径缺失**：设计 §C.2 有 W1/W2/W3，但**没有「高德现算失败」如何回退到旧 `walk_times`** 的路径（W2 是直线估算，W3 是常数），即**新增了估算，却没用上已有的实测**。建议：新导航步行 W-recovery **优先回落到 `walk_times`（我们有实测的地方）**，再才是直线估算。

### 角度 3 · 配额与性能（压下限）

- **① §A.5 估算模型哪些是拍的**：`DAU=100`、`1.5 会话/人/日`、`命中率 90%`、`回车率 20%`、`缓存命中 60%` —— **全部是拍的初值**，唯一「有依据」的是「搜索 5000/月」「LBS 150k/月」（官方）。**90% 这一条是承重墙**：降到 50% → 3150/月；降到 20% → 4500/月**月中熔断**。且 DAU 若从 100 涨到 300（推广目标），**即命中 90% 也已逼近 4000 熔断点**。
- **② 超限是「静默无效」**（协议 3.7）：用户看到的是**「搜不到」而不是报错**。设计 §A.2 有熔断 + 「提示换个说法」，**方向对**，但 §A.2 熔断后仍保留 `place/text`（也吃搜索配额）→ 自相矛盾，需修正。
- **③ 首屏总时间**：冷启 2.9s（设计）+ DB 建连 ~2.3s（若 Data Cache 未命中）+ 步行串行（P0-1，20~80s）+ 地图 JS（数百 KB）+ 首次定位（timeout 10s）。**首次访问最坏可达数十秒**；设计**没有首屏预算**。
- **④ 缓存**：步行有 `walk_cache`（先查后调）——**但键过粗**（P1-2）；搜索有 Data Cache 1h + 前端 LRU——**这层设计好**。同一 OD 反复搜：搜索不重复扣配额 ✓，步行命中缓存 ✓（前提是键修对）。
- **⑤ 并行会打爆自己的 QPS**：设计 §5 时序图「`par` 并行调用」；但 `client.ts` **明令串行 + 单进程节流**，且 QPS 3/s 全 Key 共用。真实并发（多实例/多用户）= 超限被拒。**「并行调用」与「client.ts 硬规则③」直接冲突**。

### 角度 4 · 边界与空状态

设计定义了 `NavEmptyReason`（7 项），**方向对**，但以下**未处理或处理错**：

| 场景 | 设计是否处理 | 结论 |
|------|--------------|------|
| 只有一个/两个方案 | ✗ 「不足 5 张 → 空状态」（时序图） | **缺陷**：应显示 1~4 条（P1-6） |
| 全步行方案（不坐车） | ✗ 无 | **缺陷**：短途走路更快，行业必备（P1-6） |
| 目的地就在起点旁（<100m） | 部分：`too_close` 有空状态**但无步行方案** | **半成品** |
| 收班时段 | ✓ `closed_hours` | 判定口径有混用风险（P2-4） |
| 郊区无覆盖 | ✓ `no_coverage` | 可 |
| 未开通站（ES1-ES6） | ✓ `unopened_station` | 实测**我们库里根本没有 ES1-ES6**（探针 §11 = 0 行）→ 此空状态在本库**永不触发**（只对高德影子有意义），设计已注（§B.1 脚注）但列为 `NavEmptyReason` 属冗余 |
| GPS 失败/被拒 | ✓ §D.2 降级「手动选起点」 | 可 |
| 用户在建筑物内（GPS 漂移） | ✗ | **缺**：结合 P0-2，建筑内起终点正是步行失真高发区 |
| 高德 API 挂了 | ✓ 有空状态/回退 | 可（但降级链未用 `walk_times`，见角度 2④） |
| 用户中途改出发点 | 部分（`/nav?flng=` 可传） | UI 未详述 |
| 方案很长（2h/3 换乘） | 部分（换乘 cap=2） | 无「超长警示/折叠」 |

### 角度 5 · 合规与隐私（★ 产品负责人很在意）

- **① 用户实时位置是敏感信息，但无告知/同意流程**。设计 §E 把 GPS 坐标作为**查询参数**传给 server（`?flng=&flat=`）→ 位置**上了服务端**；设计**没有**：隐私告知、首次同意、服务端不落日志/匿名化、保留期。而 `合规-高德API使用` §8.1(2) 明确要求「显著告知 + 取得**充分、有效、明确的同意**；未同意不得继续使用」。
- **② 高德声明与 logo**：设计放了 `ComplianceBar`（首页）与 `/about`，✓。但 **`/nav`、`/nav/detail` 也渲染地图**（复用 `NavMap`），§E 组件树里**这两页没有 ComplianceBar** → 遗漏（协议 7.7）。
- **③ `securityJsCode` 代理**：设计说用 `/_AMapService/` 代理「不下发明文」。**这个前提本身对**（代理在服务端加 `jscode`），但设计把代理写成 **`/_AMapService/*` 全通配转发 `restapi.amap.com/*`** → 任何人可借我们的 `jscode` 调用我们的高德账号（刷 LBS 配额），且触碰协议 **4.12.9「在自有 API 中转发本服务」**。需**路径白名单 + 来源校验**。
- **④ 「个人非商业」定位 vs 推广**：推广=用户量增长 → 搜索配额（5000/月）**先崩**（P1-3）；而**付费买流量包 = 落商业使用**（协议 4.9/3.1 + 研究 Q3 选项 C 标 🔴）→ 与「个人研究学习」冲突。**设计没有为「流量增长」留合规退路**（唯一合法路径是「本地别名库继续扩容 + 接受召回下降」，设计未把它写成明确策略）。
- **⑤ 服务地域**：协议 14.1「原则上仅面向中国大陆开发者及最终用户」，本项目最终用户在澳门 —— 设计未提示此长期风险（`合规` 文档已记，设计应引用）。

### 角度 6 · 与现有功能的兼容（会不会把现在能用的搞坏）

- **① `middleware.ts` fail-closed**：新公共页/接口不在白名单 → 公众被拒（**P1-1**）。这是**最容易上线即翻车**的一条。
- **② `client.ts` 硬规则①冲突**：`client.ts:10-12` 明文「本模块**只允许被 `src/lib/rebuild/**` 与 Cron import**；`src/lib/recommend/**` 禁止 import」。**实测当前唯一 importer 就是 `src/lib/rebuild/walk-distances.ts`**（全仓 grep 确认）。设计的 `walk-resolver` 会在 `/nav` 请求期调用 → **首个实时 importer** → 违规。设计把它说成「扩展（不改协议）」，**回避了规则①**。
- **③ `model.ts` 接缝被低估**：`modelOption` 用 `seed.planId/summary/fromSlug/toSlug`，`NavCandidate` 无这些字段（`class-diagram` 示为兄弟类型）；`walkView` 直接读 `ctx.walkIdx` 且含 zone 逻辑。改这处**必然触及旧路径**（P1-5）。
- **④ 旧数字会变**：`segment_stats` 重算已生效（P2-1）。旧 auto-line 会显示新的（更准的）时长；个别段 +50%~+89% → 可能出现「原本能赶上的卡变了档/少了卡」。需回归，但**不是缺陷，是数据升级**（取舍代价可接受）。
- **⑤ 复用 `enumerate.ts` 的纯函数**（`idxsOf/segmentsOf/deriveDirInMemory`）**判断正确** ✓ —— 这几个确为纯函数、零 DB，可安全 import。

### 角度 7 · 可测试性与可验证性

- **① 没有 ground truth**：三段式计时的输出无从校验。设计给的「高德影子对照」标了【推断】，**无量化门槛**。
- **② 可执行的验收（建议）**：定义 N 组 OD（走廊内 ≥5、走廊外 ≥5），比较「我们的 totalMin」vs「高德 `transit` 最优方案 totalMin」与「走廊内真实计时会话」，**给容差**（走廊内 ±15%、走廊外 ±30%）与**通过率门槛**（如 ≥80%）。
- **③ 立刻能做的低成本验证（不用等全功能）**：
  - 用现成 `segment_stats` + `walk_times` + 高德步行，**离线算 20 组 OD 的门到门总时长**，与高德 App 手算对照 —— 只写一个 `.verify/*.ts` 脚本即可（**本次审查已具备其全部数据依赖**）。
  - 把「步行 ratio（高德÷直线）」做成**每日采样监控**（P0-2）。

### 角度 8 · 交付节奏与风险

- **① 任务分解**：T01(L) → T03(L) → T04(L) → T05(M)，关键路径**三个 L 串行** → 一期体量大。
- **② 砍哪里最安全**：**砍地图（D/T04 的 `NavMap`/`_AMapService`）**。地图是**显示层**，`/nav` 的 5 张卡不依赖它（搜索与出卡照常，§Q7 也这么定）。**注意**：需求 3「一进页就显示地图」是产品拍板项，砍地图需产品同意 → 建议改为「地图二期，一期先用**静态占位 + 列表**」，而不是砍掉整页。
- **③ 「先上线一小块验证假设」的路径**：设计 §Q1 的**选项 C「先只做任意地点 ↔ 澳科大」**是最安全的切片 —— 保留「学校=特殊目的地」铁律、图搜索只需单向 + 少量延伸、能验证「图搜索 + 三段式计时 + 高德步行」全链路，工程量显著小。**我建议一期就用 C，而非 Q1 推荐的 A / Q5 推荐的「全放开」**。
- **④ 一期的白名单 vs 全澳**：设计 **§Q1 推荐 A（白名单）** 与 **§Q5 推荐 A（全放开任意 A→B）** 自相矛盾（P2-3）。必须二选一。
