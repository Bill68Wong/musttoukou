## 一、★ 设计决策：用「距离」承载所有实际因素

> 主人原话：**「没红绿灯，通过改距离实现」**

**做法**：不新增「红绿灯数」字段、不改模型结构 ——
把**红绿灯等待 / 绕路 / 坡度 / 楼梯 / 通关耗时**等一切实际因素，
统统折算进 `distance_m` 一个数字里 ✓

**折算关系**：
```
时间 = 距离 ÷ 1.4 m/s   ⇒   30 秒 ≈ 42 米 · 1 分钟 ≈ 84 米
```

**为什么这样好**：
| 优点 | 说明 |
|---|---|
| 不加字段 | 零 schema 变更，无需迁移 ✓ |
| 不改模型 | 沿用现有的「距离 → 时间」链路 ✓ |
| 可解释 | 一个数字，人工可核可调 ✓ |
| 影响可控 | `distance_m` **只被档 1 的衰减用**，不碰卡面显示的步行分钟 ✓ |

## 五、备注：红绿灯为什么不用单独字段

原计划「每经过一个红绿灯 +30 秒」需要先知道**红绿灯数量**，但：

| 方法 | 结果 |
|---|---|
| 高德步行 API | ❌ 实测 6 种参数、完整响应仅 16 键、**0 个**红绿灯相关字段 |
| OSM Overpass（4 镜像） | ❌ 406 / 504 / fetch failed / 返回 0 |
| 转向次数代理 | ❌ 被证伪 |
| 实地观察 | ✅ 唯一可靠 —— 但直接数红绿灯再折算，不如**直接调距离**简便 ✓ |

⇒ ★ **主人的方案更优**：实地感受直接落成距离修正，跳过了「数红绿灯」这一步 ✓
