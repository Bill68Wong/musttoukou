## 一、★ 口径定案（本次最重要的修正）

### 1.1 主人确认的事实

> 「我之前真实实测的不论是轻轨还是巴士数据，都是记的**关门时间**」

即：在 App 里按「到站 / 上车」按钮的那一刻，**车正在关门准备起步** → 记录的是**离开该站的时刻**。

### 1.2 与现有代码注释的冲突 ⚠️

`src/lib/rebuild/segment-stats.ts` 第 10~26 行写的是：

```
· board   —— 上车时刻（= 上车站发车时刻）
· alight  —— 下车时刻（= 下车站到达时刻）
段时长 = t(下一站) − t(上一站)，差里只含**起点站**的停站时间
（board 作为起点归 stop 档：上客本身即停站。）
```

**「只含起点站停站」= `dwell_A + run` = 到达口径** —— 这与主人的实际打点行为**不一致**。

若打点时刻真为「关门起步」，则：

```
t(下一站) − t(上一站) = run + dwell_B  = 离开口径
```

### 1.3 两者差多少

```
到达口径 − 离开口径 = dwell_A − dwell_B
```

实测（2026-09-13 实验一，58 对同段样本）：**均值差 −4.2 秒（≈0）· 标准差 20.6 秒 · 最大 40 秒**。

→ 均值上抵消，但**逐段误差可达 40 秒**。若新老数据口径不一致，均值会被系统性污染。

### 1.4 处置方案（三步，不阻塞开工）

| 步骤 | 动作 |
|---|---|
| ① 采集端 | **双口径都算**（原始帧已含 status 翻转，两种口径零额外成本） |
| ② 数据核查（可选） | 用 `timer_events` 的 `station_arrive` 与实测车速/停站时长比对，反推现有 `segment_stats` 的真实口径，拿到书面证据 |
| ③ 定案后 | 统一 `segment_stats` 的口径定义 + 修正代码注释 + 决定历史数据是否需要重算 |

> **不阻塞的理由**：采集只存原始帧，口径是**事后计算时选的**。改口径不需要重采。

## 二、范围与请求速率预算（回答「全澳 92 条能做到吗」）

### 2.1 技术可行性

| 维度 | 评估 | 依据 |
|---|---|---|
| 客户端吞吐 | ✅ **可行** | 单帧延迟实测 9~64ms（均 ~20ms）；92 条串行 = **1.84 秒/轮** < 5 秒预算 |
| 请求速率 | 18.4 次/秒 | 92 ÷ 5 秒 |
| DSAT 承载 | ⚠️ **未知** | 无实测数据；单一 IP 18.4 次/秒是明显异常特征 |
| 封禁后果 | 中 | 采集中断；可换 IP / 等解封，无数据损失（原始帧已落盘） |
| 合规 | ⚠️ | 频率越高越像爬虫；官方接口未开放个人申请 |

**结论：技术上能做到，但风险未经验证，不建议一次到位。**

### 2.2 推荐方案：分级轮询（★ 请求速率不随线路数线性增长）

| 组 | 线路 | 频率 | 单线有效精度 | 请求速率 |
|---|---|---|---|---|
| **A 组（核心）** | **25 / 25AX / 26 / 50 / 51 / 51A / 51B / 59** | **每 5 秒** | **5 秒** | 1.6 次/秒 |
| B 组（其余） | 其余 84 条，分 12 组轮换 | 每 5 秒轮一组 | 每线 60 秒 | 1.4 次/秒 |
| **合计** | 全澳 92 条 | — | — | **3.0 次/秒** |

**对比基准**：DSAT 官网前端单个用户 = **0.1 次/秒**。

- 纯 A 组：16× 官网单用户
- A+B 方案：**30× 官网单用户**（全澳 92 条全速方案的 1/6）
- 全速方案：**184× 官网单用户** ⚠️

> **为什么 A 组是这 8 条**：`docs/采集清单-v3` 的真缺 54 段**全部**落在这 8 条线上。
> 其余 84 条属「为将来扩展储备」，60 秒精度对「站间时长建模」已够（用于交叉验证与共享键扩展）。

### 2.3 灰度路径（先验证再提速）

| 阶段 | 内容 | 观察指标 |
|---|---|---|
| 第 1 轮 | **仅 A 组**（1.6 次/秒） | 失败率 = 0？延迟稳定？ |

## 三、采样调度设计

### 3.1 单轮结构（5 秒窗口）

```
t=0.00s  → 查 A 组 8 条（串行，约 0.16 秒）
t=0.20s  → 查 B 组的当前组（约 0.14 秒）
t=0.40s  → 本轮结束，空闲
t=5.00s  → 下一轮
```

- **错峰**：两组之间留 200ms，避免瞬间并发
- **抖动**：每轮起始加 ±300ms 随机抖动，避免完美周期性（更接近人类行为）
- **预算**：一轮总耗时 < 0.5 秒，占 5 秒预算的 10% → 余量充足

### 3.2 采集持续时间

**单次 30 分钟**（主人已定）。理由：

- 全速方案下 92 条线并行，30 分钟 = 360 帧，已能覆盖大量车辆行程
- 30 分钟足够拿到「真实失败率」这一关键观察量（全速首轮是未知海域，不宜一次压太久）
- 粗估约 **10,000 个段观测 / 轮**（92 条线 × 平均 6 辆在线 × 约 18 段）
- 若 30 分钟稳定，可再延长；站间时长的日内周期靠「一天多次 + 窗口分散」覆盖

### 3.3 时间窗口建议（覆盖时段，避免采样偏差）

| 窗口 | 时段桶 | 说明 |
|---|---|---|
| 07:00–08:30 | `am_peak` | 早高峰（最高价值） |
| 13:00–14:30 | `day` | 平峰 |
| 17:30–19:00 | `pm_peak` | 晚高峰 |
| 21:30–23:00 | `night` | 夜间（可选，若需夜间样本） |

> ⚠️ **要避免的坑**：只在晚上采集 → 样本全挤在 `night` 桶 → 模型系统性低估高峰时长。
> 这是**采样偏差**，事后无法用任何算法弥补。

## 四、采集字段清单

### 4.1 逐帧逐车（每 5 秒 × 每辆车一条记录）

| 字段 | 类型 | 用途 |
|---|---|---|
| `frame_ts` | ISO 字符串 | 帧时刻（澳门时间 + UTC） |
| `frame_ms` | int64 | epoch 毫秒 → 算时长 + 分时段 |
| `route` | text | 线路号 |
| `plate` | text | 车牌 → 逐车追踪 |
| `status` | `'1'`/`'0'` | **1=停靠 / 0=已离站 → 判「到达/离开」的唯一依据** |
| `sta_code` | text | 挂载站原始码（含站台号如 `T376/1`） |
| `main_code` | text | 归一主码（`T376`）→ 跨线路共享键 |
| `sta_idx` | int | 站序下标 → 判相邻站对、判甩站 |
| `speed` | text | 原始字段（**诊断用，禁止参与状态判定**） |
| `passenger_flow` | text | 拥挤度原始值 |
| `bus_type` / `bus_code` / `is_facilities` | text | 原始字段留档 |
| `req_ms` | int | 该请求耗时 → 监控 DSAT 负载 |

### 4.2 每线路一次（元数据）

- 站序快照：全部 `sta_code` + `sta_idx`（含站台号，用于环线首尾同码处理）
- 采集参数：`interval` / 线路分组 / 起止时刻
- 环境信息：脚本版本、输出路径

### 4.3 事后派生（不占采集带宽）

| 派生量 | 口径 |
|---|---|
| 到达时刻 | 首次出现 `s1` 于该站 |
| 离开时刻 | 首次出现 `s0` 于该站（且此前见过 `s1` 同站） |
| 段时长（到达口径） | `t(停稳@B) − t(停稳@A)` |
| 段时长（离开口径） | `t(离@B) − t(离@A)` ← **主人手动数据的口径** |
| 停站 dwell | `t(离@X) − t(停稳@X)` |
| 时段分层 | `weekday` + `time_bucket`（am_peak/day/pm_peak/night） |
| 共享键 | `(mainCode(from), mainCode(to), weekday, bucket)` |

## 五、运维与风控

| 措施 | 说明 |
|---|---|
| 失败退避 | 连续失败 3 次 → 自动中止本轮（不硬撑） |
| 延迟监控 | 记录每帧 `req_ms`；若均值翻倍 → 疑似限流，自动降频 |
| 随机抖动 | 每轮 ±300ms，避免完美周期特征 |
| 分批错峰 | A/B 组之间留 200ms |
| 只读保证 | **不发任何写库请求**；不触碰生产 `src/` |
| 数据落盘 | 每帧 `append` 写入 JSONL（**中途中断不丢已采数据**） |
| 记账 | 记录全部请求的时刻 / 耗时 / 结果，供事后合规审计 |
