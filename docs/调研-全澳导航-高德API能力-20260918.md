## 0. 结论速览

### 0.1 一句话结论

**技术上可行，但不是「接高德就完事」。** 高德在澳门的公交数据**意外地好**（92 条巴士 + 3 条轻轨全覆盖、错别字容错极强、默认就给 4~5 个方案且可拉到 10 个），完全可以当**候选生成器 + 站序来源 + 步行段计算器**；但**车程仍只能覆盖我们已有实测的 13/95 条线路**，且当前「自动选线」的候选枚举链路是**手工计划驱动**的，全澳推广必须先改造成**图搜索驱动**。

### 0.2 用户原始需求（复述）

1. 调研高德 API 能力，**特别是：返回公共交通方案时是只给一个「最优」，还是给多个？**
2. 首页改为**搜索页**，用户输入目的地
3. 输入时**实时推荐**；要处理**打错字 / 地名多样化**，保证「返回正确目的地」
4. 确认目的地后**默认从「我的位置」出发**（需实时定位），也可改出发点
5. 点「出发」看到**五个用时最短方案**，含实时报站；其中**首末步行段用高德**、**车程用我们自己的实测数据**
6. 点卡片进**详情页**（本次不做开发者模式）
7. **地图地基**：搜索页有地图 + 实时位置图标；输入目的地后显示目的地图标。线路与巴士实时位置是**远期目标**

### 0.3 三个最关键的发现（先看这三条）

| # | 发现 | 影响 |
|---|---|---|
| ① | **高德 v5 公交路径规划默认返回 4~5 个方案**；用 `AlternativeRoute=1..10`（★**驼峰命名**，写 `alternative_route` 会**静默失效**）可拉到最多 10 个，实测拿到 1/2/3/4/5/6/7 个 | 【需求 1】答案：**给多个**。但**不建议直接拿高德的方案当我们的 5 张卡**（口径不同），应只取「候选与站序」 |
| ② | **个人认证开发者的「基础搜索服务」配额只有 5,000 次/月**（输入提示 / 关键字搜索 / 周边搜索都算在内），而「基础LBS服务」（路径规划/步行/地理编码）是 150,000 次/月 | 【需求 3】的「实时输入提示」是**配额杀手**：5,000/月 ≈ 166 次/天。**必须本地优先 + 兜底高德**，不能逐字打高德 |
| ③ | 我们自己的 `segment_stats` 只有 **475 行 / 105 个不同邻接站对 / 13 条线路**；全澳是 **95 条线 / 119 个方向 / 2,751 个有向段** ⇒ 站对级实测覆盖率 **≈ 3.8%**；`transfer_walks` 只有 **2 条** | 【需求 5】「车程用我们自己的数据」在校园走廊以外**基本无数据**，全澳推广必须**继续采集或接受估算回退** |

## 2. 【A】高德地图开放平台能力盘点（Web 服务 API + JS API）

### A1. 公共交通路径规划（公交 / 地铁 / 轻轨）

#### A1.1 端点与请求结构

| 版本 | 端点 | 状态 |
|---|---|---|
| **v5（推荐）** | `GET https://restapi.amap.com/v5/direction/transit/integrated` | 【实测】澳门可用，字段最全，支持 `AlternativeRoute` |
| v3（旧） | `GET https://restapi.amap.com/v3/direction/transit/integrated` | 【实测】澳门可用，但**不支持**方案数控制（实测传 `alternative_route=3` 仍固定返回 4） |

**v5 关键请求参数**【实测 + 官方/镜像文档】：

| 参数 | 必填 | 实测行为 |
|---|---|---|
| `origin` / `destination` | ✅ | `lng,lat`（**经度在前**），小数 ≤6 位 |
| `city1` / `city2` | ✅ **必填** | 【实测】省略 → `status=0 MISSING_REQUIRED_PARAMS`；传 adcode `820000` ✅ 通过；传 citycode `1853` ✅ 通过；传中文 `澳门` → `INVALID_PARAMS` ✗ |
| `ad1` / `ad2` | ❌ | 【实测】只传 `ad1/ad2` 而缺 `city1/city2` 仍报 `MISSING_REQUIRED_PARAMS` |
| `strategy` | ❌ | 【实测】澳门 **0~8 全部有效**（见 A1.4） |
| **`AlternativeRoute`** | ❌ | ★★【实测】**方案条数控制，取值 1~10**。注意**大写 A + 大写 R**；`alternative_route` 小写**被静默忽略** |
| `nightflag` | ❌ | 【实测】给了 `date/time` 后再给 `nightflag=1` 无变化 |
| `date` / `time` | ❌ | 【实测】有效，用于「按出发时刻筛可乘线路」（见 A1.5） |
| `originpoi` / `destinationpoi` | ❌ | 【实测】`strategy=6`（地铁图模式）**必须**同时传，否则 0 方案 |
| `show_fields` | ❌ | 【实测】`cost,transits`；加 `polyline` 会显著增大响应，**且实测方案数从 5 变 4** ⚠️（详见 §6 坑#2） |

#### A1.2 ★★ 关键问题：一次请求返回几个方案？

> **答案：默认 4~5 个（不是 1 个）。并且可以用 `AlternativeRoute` 精确控制 1~10 个。**

**实测证据（关闸 → 澳科大，同一 OD，连续调用）**：

| 调用 | `AlternativeRoute` | 返回 `route.transits` 条数 |
|---|---|---|
| 不传 | — | **5** |
| `alternative_route=1`（小写） | 被忽略 | **5** ← ✗ 未生效 |
| `AlternativeRoute=1`（驼峰） | 1 | **1** ✓ |
| `AlternativeRoute=2` | 2 | **2** ✓ |
| `AlternativeRoute=3` | 3 | **3** ✓ |
| `AlternativeRoute=4` | 4 | **4** ✓ |
| `AlternativeRoute=5` | 5 | **5** ✓ |
| `AlternativeRoute=6` | 6 | **6** ✓ |
| `AlternativeRoute=8` | 8 | **7** ← 该 OD 只有 7 个可行解 |
| `AlternativeRoute=10` / `=20` | 10 / 20 | **7**（上限截断，不报错） |

**其他 OD 的默认方案数**【实测】：

| OD | 默认方案数 | 备注 |
|---|---|---|
| 关闸 → 澳科大 | 4~5 | 同一 OD 因 `show_fields` 不同出现过 4 与 5 |
| 妈阁轻轨站 → 科大轻轨站 | 5 | 含 1 条纯轻轨直达 |
| 氹仔码头轻轨站 → 排角轻轨站 | 5 | 含 1 条纯轻轨 |
| 妈阁 → 路环码头（长距离） | 5 | |
| 九澳（路环东郊）→ 氹仔码头 | 5 | |
| **珠海拱北口岸 → 澳科大（跨境）** | **2** | 跨境方案明显变少 |
| **澳门半岛西侧海面（异常点）→ 澳科大** | **1** | 退化到 1 个 |
| `strategy=6` 缺 `originpoi` | **0** | 参数不当会返回 0 |

**官方是否规定数量？** ——【官方】`/v3/direction/transit/integrated` 参数表**未列出** `alternative_route`；v5 的该参数在官方页面的检索快照中出现（「AlternativeRoute：返回方案条数，可传入 1-10」），第三方封装文档亦写「公交最多 5 种方案」。**⇒ 结论：数量上限按「平台实现 10 / 默认可算 4~5」理解；不要依赖固定值，要按数组长度处理。**

#### A1.3 返回字段（实测确认）

```
route
├─ origin / destination / distance / cost
└─ transits[]                      ← ★ 方案数组（1~10 条）
   ├─ cost.duration                ← 总时长（秒）
   ├─ cost.transit_fee             ← 票价（元/MOP，实测 "6.0" / "12.0"）
   ├─ distance / walking_distance  ← 总里程 / 总步行距离（米）
   ├─ nightflag                    ← 0=非夜班 1=夜班
   └─ segments[]                   ← 按顺序的路段
      ├─ walking                   ← 步行段
      │  ├─ origin / destination
      │  ├─ distance（米）
      │  ├─ cost.duration（秒）
      │  └─ steps[] { instruction, road, distance, action, polyline }
      └─ bus                       ← 乘车段
         └─ buslines[]             ← 该段的候选线路（同段可能多条线并行）
            ├─ name                ← "25路(关闸总站(C车道)--关闸总站(C车道))"
            ├─ id                  ← "820000010058"
            ├─ type                ← "普通公交线路" / ★"地铁线路"（澳门轻轨）
            ├─ distance / cost.duration / via_num
            ├─ departure_stop { name, id, location, entrance{name,location} }
            ├─ arrival_stop   { name, id, location }
            ├─ via_stops[]    { name, id, location }   ← ★ 完整途经站序
            ├─ polyline
            └─ start_time / end_time / station_start_time / station_end_time
```

**字段可用性实测（⚠️ 与直觉不同）**：

| 字段 | 实测可用性 |
|---|---|
| 步行段 `distance` / `cost.duration` | ✅ **稳定可用**（这是【需求 5】最关键的两个数） |
| 乘车段 `buslines[].name` / `type` / `distance` / `cost.duration` / `via_num` | ✅ 可用 |
| 上/下车站 `departure_stop` / `arrival_stop`（含 GCJ-02 坐标） | ✅ 可用 |
| `via_stops` 完整途经站序 | ✅ 可用（可用来做「站码映射」） |
| **票价** `buslines[].cost.ticket_price` | ❌ **实测在澳门基本不返回**；票价只在 `transits[].cost.transit_fee` 层面有 |
| **首末班** `start_time` / `end_time` | ⚠️ **大部分线路为空**，个别有（实测 28B → `0615/2345`，103 → `0600/2330`）；`station_start_time`/`station_end_time` 未观察到 |
| `walking.steps[].polyline` | ⚠️ **形态随 `show_fields` 变化**：`show_fields=cost,transits` 时是**对象** `{"polyline":"..."}`；项目现有调用（`show_fields=cost,polyline`）拿到的是**字符串** → 解析需兼容两种（详见 §6 坑#2） |

#### A1.4 `strategy` 策略（v5 实测 0~8 全有效）

【实测，以「妈阁 → 氹仔码头轻轨站」为例】

| 值 | 含义（v5） | 实测首方案 | 方案数 | 备注 |
|---|---|---|---|---|
| 0 | 推荐模式（同高德 App 默认） | 氹仔线 32min | 5 | |
| 1 | 最经济（票价最低） | 氹仔线 32min | 5 | 与 0 结果一致（轻轨票价未必最低） |
| 2 | 最少换乘 | 氹仔线 32min | 5 | 与 0 一致 |
| 3 | 最少步行 | 氹仔线 32min | 5 | 第 4/5 名换成了短步行组合 ✓ 生效 |
| 4 | 最舒适（空调车） | 氹仔线 32min | 5 | 与 0 一致 |
| **5** | **不乘地铁（= 不乘澳门轻轨）** | **26路 51min** | 5 | ✓ 生效：**所有轻轨方案被剔除** |
| 6 | 地铁图模式 | （无 `poiid` → 0 方案） | 1（配 poiid 后） | 必须传 `originpoi`+`destinationpoi` |
| 7 | 地铁优先 | 氹仔线 32min | 5 | ✓ 生效：第 4 名变成「氹仔线 + MT1」 |
| 8 | 时间短（方案总时间最少） | 氹仔线 32min | 5 | ✓ 生效：末段换成了 36路/MT1 组合 |

> 【官方】v3 的 `strategy` 只有 0/1/2/3/5 五档；v5 扩到 0~8。**本项目建议**：默认用 `strategy=0`（与高德 App 一致），另提供 UI 开关映射到 5（不乘轻轨）/3（最少步行）。

#### A1.5 `date`/`time`：运营时间外的「无方案」状态

【实测，关闸 → 澳科大，`date=2026-09-18`】

| 时刻 | 方案数 | 实测首方案 |
|---|---|---|
| 05:00 | 5 | 51A |
| 08:00 | 5 | 51A / 51B / 51 / AP1 / 30X |
| 23:50 | **3** | 51A / AP1 / 51 |
| **03:00** | **3** | 51A / **N2（夜间巴士）** / 101 → N2 |
| 03:00 + `nightflag=1` | 3 | 同上（已给 `date/time` 时 `nightflag` 无额外作用） |

**⇒ 结论**：高德**有能力**按时刻筛选，并**知道澳门的夜间巴士 N 线**。但：
- 高德**不会**返回「无方案」错误码 —— 它总能凑出一些方案（甚至夜间也给了 3 条）。**「运营时间外」的状态判定必须我们自己算**（项目已有轻轨时刻表 `lrt_timetables` + DSAT 实时数据）。
- 跨境夜班 `101` 也出现在结果里，说明高德对跨境线有数据。

#### A1.7 批量与配额

| 项 | 数值 | 依据 |

### A4. 浏览器定位 / 地图 JS API

#### A4.1 网页里获取用户实时位置的标准做法

| 方式 | 说明 | 推荐度 |
|---|---|---|
| **高德 `AMap.Geolocation` 插件**（JS API） | 融合 **HTML5 Geolocation + 精确 IP 定位 + 安卓定位 SDK**，多源互备；`getCurrentPosition(cb)` 回调 `status: 'complete'|'error'`；返回 `data.position`(AMap.LngLat) · `data.location_type` · `data.accuracy`(米) | ★★★ **推荐** |
| 浏览器原生 `navigator.geolocation` | 返回 **WGS84**，需自己转 GCJ-02；国内偏差大、城市级粗略（尤其 iOS Safari） | ★ 仅作兜底 |
| `AMap.CitySearch` | 只到**城市级**（`getLocalCity`），快，但不适合「我的位置」 | ★ 不适用 |

**关键参数**【官方】

```js
new AMap.Geolocation({
  enableHighAccuracy: true,   // 高精度，默认 true
  timeout: 10000,             // 超时（默认无穷大）
  convert: true,              // ★ 自动偏移坐标，偏移后的坐标为高德坐标（GCJ-02），默认 true
  showButton: true,           // 定位按钮
  showMarker: true,           // 定位成功后显示点标记（自定义图标时置 false）
  showCircle: true,           // 用圆圈表示精度范围
  panToLocation: true,        // 定位后地图中心移到定位点
  zoomToAccuracy: true,       // 自动调整视野使精度范围可见
});
map.addControl(geolocation);
geolocation.getCurrentPosition((status, result) => { /* status==='complete' */ });
```

**前提条件**【官方】：
- 必须 **HTTPS**（iOS 10+ 与部分 Android 已禁止非安全域定位）→ ✅ 项目 `musttoukou.vercel.app` 已满足
- 移动端需：系统 GPS 开 / 浏览器已授权定位
- **PC 无 GPS 走 IP 定位，失败率约 5%**
- 室内 / 手机信号差会导致精度下降

#### A4.2 ★ 坐标系问题（WGS84 ↔ GCJ-02）

| 场景 | 处理方式 |
|---|---|
| ★ **用户手机 GPS（WGS84）→ 高德地图（GCJ-02）** | **不要自己转！** 用 `AMap.Geolocation({ convert: true })`（默认已开）→ `data.position` **直接就是 GCJ-02**。JS API 2.0 亦提供 `AMap.convertFrom(lnglat, 'gps', cb)` 做显式转换（支持 `gps/baidu/mapbar/autonavi/gcj02`）【官方】 |
| 高德返回的 POI / 路径坐标 | **原样使用**（已是 GCJ-02），**绝不能再转一次** |
| ★ **我们库里的坐标（DSAT，WGS84）→ 上地图 / 传高德 API** | 必须 `wgs84ToGcj02()`。项目已有 `src/lib/amap/coord.ts`，与高德官方转换最大差 **0.32m** ✓ |

> ⚠️ **项目已踩过的坑**：`coord.ts` 头注释记录「不转换时步行距离系统性偏大一倍」（4741m vs 2370m）。**全澳推广时这个坑会在每一个新地点重现** —— 只要有任何一处忘记转换，那一条步行时长就是错一倍的。

#### A4.3 Key 是否要分开申请？—— **要**

| 项 | Web 服务 API Key（现有） | **JS API Key（需新增）** |
|---|---|---|
| 服务平台类型 | 「Web 服务」 | **「Web 端 (JS API)」** |
| 是否同一个 Key 通用 | ❌ **不通用，必须分别创建** | ❌ |
| 是否需要安全密钥 | 不需要 | ★ **需要 `securityJsCode`**（2021-12-02 后申请的 Key 必须配） |
| 域名白名单 | 可留空（现有 Key 就是留空） | **建议配**（`musttoukou.vercel.app`） |
| 配额归属 | 基础LBS服务 / 基础搜索服务 | 基础地图定位服务（JS 地图图面初始化） |

**安全密钥的两种用法**【官方】：
1. **代理转发（强烈建议，安全）**：在 Node/Nginx 侧用 `/_AMapService/` 前缀把 `jscode` 附加后转发到 `https://restapi.amap.com/`，前端**不下发明文密钥**。
   ⚠️ Vercel 无 Nginx，但可以用 **Next.js Route Handler 或 middleware** 实现等价的转发层（【推断】可行）。
2. **明文设置（不推荐生产）**：`window._AMapSecurityConfig = { securityJsCode: "..." }`，必须在 JS API 脚本加载**之前**设置。

> ★ **额外收益**：安全密钥的 `/_AMapService/` 代理**同时代理 Web 服务 API** → 意味着原本需在服务端调用的 Web 服务请求也可以走这条通道，**降低 Vercel Serverless 冷启动往返**（项目已知痛点：函数在 `iad1`、库在 `ap-southeast-1`，冷启动建连 ~2.3s）。

### 3.1 从竞品得到的 4 条设计启示

1. **方案数**：行业共识是 **3~6 条**。我们要 5 条 = 合理（Citymapper 6、Moovit 3-4、国内 3）。**但「5」应当是「最多 5 条」，不是「凑满 5 条」** —— 空旷时段/郊区很可能只有 1-2 条可行解（实测高德在异常点只给 1 条），UI 必须能优雅降级。
2. **排序主轴 = 总门到门耗时**，**并列显示**「步行距离 / 换乘次数 / 票价 / 赶车档」，这是全行业一致的信息架构；我们的「赶车 5 档」是**独家差异化**（竞品都没有针对「下一个班次能不能赶上」的门到门建模）。
3. **策略过滤器**（走路少 / 少换乘 / 最快 / 不乘轻轨）可以直接映射到高德 `strategy` 参数（实测 3 / 2 / 8 / 5 均有效）→ 成本极低，收益明显。
4. **澳门本地特有、且我们独有的机会**：
   - 澳门有**两套官方 App 且互有短板**（《巴士報站》准但功能窄；《澳門出行》全但巴士不准）→ 我们可以做「**准 + 全**」。
   - **跨境生源**是我们的核心用户，而「**口岸实时通关时长**」是全行业都没解决的痛点（DSAT 有数据但我们不确定其接口可用性）→ **这是最值得投入的差异化**。

## 4. 【C】结合本项目的可行性判断（重点）

### C1. 【需求 5】「步行用高德、车程用我们自己的数据」—— 技术上可行吗？

> **结论：架构上可行，且高德刚好提供了我们需要的那一半。但有两处硬约束会让「车程用我们自己的数据」在全澳范围内退化成「估算」，必须在产品上诚实表达。**

#### C1.1 逐段拆解

| 段 | 数据来源 | 现状 | 可行？ |
|---|---|---|---|
| **我的位置 → 上车站**（步行） | 高德 `/v5/direction/walking` | ✅ 项目已在用（`src/lib/amap/client.ts`），限速/坐标转换/吸附距离自检都已就绪 | ✅ **完全可行** |
| **候车时间** | DSAT 实时报站（巴士）+ 我们库的轻轨时刻表 | ✅ 已有 | ✅ 可行 |
| **乘车（站间行车）** | 我们自己的 `segment_stats`（逐跳累加，禁止「站数 ×常数」） | ⚠️ **只覆盖 13/95 条线路、105/2751 个有向邻接站对 ≈ 3.8%** | 🟡 **校园走廊内可行；全澳大部分只能回退估算** |
| **换乘步行** | 我们自己的 `transfer_walks` 实测 | 🔴 **只有 2 条** | 🔴 **基本无数据**，需补采或退回高德步行 |
| **下车站 → 目的地**（步行） | 高德 `/v5/direction/walking` | ✅ 同上 | ✅ **完全可行** |

#### C1.2 为什么要「只看高德的步行、不用高德的车程」

项目内已有明确口径冲突记录（`src/lib/amap/client.ts` 头注释 ②）：

> 高德返回的 `duration` **不能**当 `minutes` 用 —— 口径不同，否则会**双重缩档**。

再加上本次实测的新证据：
- 高德给的是「**站**」级，我们库里是「**站台**」级（`T363/1` `T363/2` `C690/1..3`）。方向靠错就会反向坐车 → 需要按方向推断站台。
- 高德的车程时长来自它的路网速度模型，**不是**澳门巴士的真实到站间隔；我们的 `segment_stats` 来自 DSAT 报站实测（含停站），这才是用户体感的「到站间隔」。

⇒ **组合方式是正确且必要的**：高德负责「几何/网络/步行」，我们负责「时间/班次/赶车」。

#### C1.3 推荐的组合架构（可直接给架构师）

```
用户输入目的地（POI，GCJ-02）
        │
        ├─(1) 首末步行：高德 walking（我 -> 上车站 / 下车站 -> 目的地）
        │       · 输入：我们的 WGS84 坐标 → wgs84ToGcj02() 后提交
        │       · 输出：distance_m（项目已有 snap_start/snap_end 自检）
        │
        ├─(2) 骨架枚举：★ 本地图搜索（推荐）或 高德 transit/integrated（备选）
        │       · 本地：用 route_stations（2,870 行 / 610 站 / 119 方向）
        │         做「换乘 ≤2 次」的路径搜索 → 零配额、站码天然对齐
        │       · 高德：AlternativeRoute=5~10 拿候选 + 用 via_stops 做交叉校验
        │
        ├─(3) 站码映射：高德站名/坐标 → 我们的 DSAT 站码
        │       · 坐标法：高德 GCJ-02 → gcj02ToWgs84()，最近邻 ≤60m
        │         【探针4 实测成功率：氹仔 94% / 澳科大 3km 82%】
        │       · 名称法：繁简归一 + 去「公交站/總站/站」后缀（高德是简体，我们是繁体）
        │       · 两法交叉验证，双失配则丢弃该候选（不猜）
        │
        ├─(4) 车程：对每一跳调 lookupHop() → 已有 6 级回退链
        │       · L1 本线·今日·stop → L2 本线·全周·stop → L3 本线·全周·all
        │       · L4 跨线邻接共享 → L5 该线单站均值 → L6 全局单站均值
        │       · ⚠️ 必须把「回退层级」透传到 UI（L5/L6 = 估算，不是实测）
        │
        ├─(5) 候车：DSAT 实时（巴士）/ lrt_timetables（轻轨）
        │
        └─(6) 时间轴 = 步行(高德) + 候车(实时) + 车程(自己) + 换乘步行(自己)
                 → 排序取前 5 → 「赶车 5 档」判定
```

**关键设计建议**：
1. **候选枚举从「手工计划」换成「本地图搜索」**（见 C2）—— 这是全澳推广的**前置工程**，不做的话任意 OD 出不来候选。
2. **`station_walk_distance` 的角色要从「离线缓存 37 组」升级为「实时按需查询 + 缓存」**：全澳任意地点组合是无限的，不能预扫；
   - 策略：**首次查询走高德 → 落表 → 后续复用**（`fetched_at` + `RETTL_DAYS=30` 已有）；
   - ⚠️ 但这会打破「稳态日调用≈0」的现状 → **配额要重新评估**（见 A5.2：LBS 150,000/月仍有很大余量）。
3. **必须给「步行为主」的方案留位置**：实测郊区场景（九澳 → 氹仔码头）出现「走 2064m」这种段；且短距离时**步行可能比等车更快** —— 行业里 Citymapper/Google 都会给「纯步行」方案，建议补上。

**三个候选来源对比**：

| 来源 | 覆盖率 | 配额成本 | 与我们的口径对齐 | 结论 |
|---|---|---|---|---|
| **① 我们自己的 `route_stations`（本地图搜索）** | ✅ 全澳 95 条线 / 610 站 / 119 方向 / 2,870 行**已全量在手** | **0** | ★★★ 站码天然一致、方向可用、`segment_stats` 直接挂得上 | 🥇 **主力** |
| **② 高德 `transit/integrated`（`AlternativeRoute=10`）** | 好 | LBS 150,000/月，单次 | ⚠️ 需站码映射（探针4：82-94% 可映射） | 🥈 **辅助/交叉校验**：帮我们「发现」想不到的直达组合 + 提供首末步行段 |
| **③ 高德 `bus/linename`（全量线路 + 站序 + polyline）** | ✅ 实测对澳门有效（`keywords=25` → 25 路完整 polyline；`keywords=氹仔线` → 地铁线） | 搜索配额（5000/月）⚠️ | ⚠️ 繁体/简体差异 | ⬜ **不建议**：我们已有 DSAT 官方站序（2870 行），**重复抓取既费配额又触碰条款 3.5/4.12.3（抓取服务数据）** |

**⇒ 推荐枚举算法（本地图搜索）**：

```
输入：上车站集合 S_from（我位置 步行可达的 ≤N 个站）
      下车站集合 S_to  （目的地 步行可达的 ≤N 个站）
      （S_from / S_to 用高德 place/around types=150700|150500 得到，或本地 610 站全量做距离筛选）

搜索：在「线路 × 站序」图上做 BFS，换乘次数 ≤ 2
  · 直达：某条线能 S_from[i] → S_to[j]
  · 1 次换乘：S_from[i] --线A--> X ，X --线B--> S_to[j]（含同站换乘 / 相邻站步行换乘）
  · 2 次换乘：（轻轨 + 巴士混合场景需要）
候选剪枝：
  · 总步行 > 1.5km 丢弃
  · 绕路系数 > 2.5 丢弃
  · 线路在运营时间外丢弃（用 DSAT 实时 + lrt_timetables）
  · 类型黑名单过滤（穿梭巴士等）
```

> ✅ **这个算法完全离线、零配额、可控**，而且能直接复用现有的 `segment-lookup.ts`（逐跳累加）、`enumerate.ts`（站序解析 / `idxsOf` / `segmentsOf` / `deriveDirInMemory`）、`model.ts`（建模/排序）。**改造量主要在「候选来源」这一处**，下游链路可原样复用。

**同时建议保留高德作为「影子对照」**：内部把高德返回的方案与我们的方案做 diff，用来发现「我们漏了哪条线」——这是最省成本的数据质量监控（【推断】）。

### C4. 【需求 7】地图地基的最小实现

#### C4.1 需要什么

| 项 | 内容 |
|---|---|
| **Key** | ★ **新增一个「Web 端 (JS API)」平台的 Key** —— 现有「Web服务」Key **不能**用于 JS API |
| **安全密钥** | 同一应用下申领 `securityJsCode`；建议走 **Next.js Route Handler 做 `/_AMapService/` 代理**，不下发明文 |
| **库** | `https://webapi.amap.com/maps?v=2.0&key=<JSKEY>`（`AMap.Geolocation` / `AMap.Marker` 按需 `AMap.plugin()` 异步加载） |
| **配额** | 基础地图定位服务 **1,500,000/月**（个人认证）→ 只要不是「每次渲染都 new Map」，完全够用 |
| **合规** | 页面**必须**显示「本服务来源于高德地图」+ 保留高德版权/审图号（协议 7.7 / 4.10.7） |

#### C4.2 最小实现（底图 + 我的位置 + 目的地标记）

```tsx
// 1) 安全密钥配置（必须在 JS API 脚本加载前）
window._AMapSecurityConfig = { serviceHost: "/_AMapService" };   // 或 securityJsCode（仅开发）

// 2) 底图
const map = new AMap.Map(container, { zoom: 15, viewMode: "2D", resizeEnable: true });

// 3) 我的位置（★ convert:true 自动把 GPS 的 WGS84 转成 GCJ-02，不要再自己转）
AMap.plugin("AMap.Geolocation", () => {
  const geo = new AMap.Geolocation({
    enableHighAccuracy: true, timeout: 10000,
    convert: true, showMarker: false, showCircle: true, zoomToAccuracy: true,
  });
  geo.getCurrentPosition((status, r) => {
    if (status !== "complete") { /* 降级：让用户手动选起点 */ return; }
    // r.position 已是 GCJ-02；r.accuracy 是精度（米）；r.location_type 是来源
    new AMap.Marker({ position: r.position, content: '<div class="user-dot"></div>' }).setMap(map);
  });
});

// 4) 目的地图标（★ 用高德返回的 POI location 原样使用，已是 GCJ-02）
new AMap.Marker({ position: [lng, lat], icon: new AMap.Icon({ /* ... */ }) }).setMap(map);

// 5) 页面上放「本服务来源于高德地图」+ 埋点：不要把地图实例放进会频繁重渲染的组件
```

#### C4.3 坐标系处理三条铁律（全澳推广时每处都要遵守）

| # | 场景 | 做法 |
|---|---|---|
| ① | 用户手机 GPS（WGS84） | **不要自己转** → `Geolocation({convert:true})` 或 `AMap.convertFrom(lnglat,'gps')` |
| ② | 高德返回的 POI / 路径坐标（GCJ-02） | **原样用，绝不再转** |
| ③ | 我们库里的坐标（DSAT，WGS84） | 上地图 / 传 API 前 **必须** `wgs84ToGcj02()`（`src/lib/amap/coord.ts`，误差 0.32m） |

### 6.1 API 层面的「静默坑」（最危险，因为不报错）

## 7. 我最想让产品负责人澄清的 3 个问题

### 问题 1：车程数据的缺口怎么处理？——「补采到全澳」还是「接受估算并明示」？

现状：`segment_stats` 只覆盖 **13/95 条线路（3.8% 的站对）**，`transfer_walks` 只有 **2 条**。全澳推广后，绝大多数路线的「车程」将落在回退链的 L5/L6（该线单站均值 / 全局单站均值）——**那不是实测，是估算**。

- **选项 A**：先按「校园走廊内实测、走廊外明示估算」上线，UI 用不同标识区分（成本低，但用户可能觉得「同一 App 里两个口径」）
- **选项 B**：暂停开发，先花 N 周把全澳主干线（跨区线路 ~20 条）的段时长采出来（成本高、周期长，但产品一致性最好）
- **选项 C**：走廊外直接用高德的时长（口径不一致，但至少是「有意义的路网时间」而不是「全局均值」）

> 我的推荐：**A + C 混合** —— 实测优先，其次高德路网时间，最后才是站均值；三档在 UI 上明确区分。但这需要您拍板「一致性 vs 交付速度」的取舍。

### 问题 2：搜索配额 5,000 次/月是硬约束，产品形态要不要为它让路？

我实测确认：**输入提示 / 关键字搜索 / 周边搜索同属「基础搜索服务」，个人认证只有 5,000 次/月**（LBS 服务是 150,000/月，差 30 倍）。按日活 100 人、每人一次搜索、逐字提示不防抖测算，**一个月就会超限**；而超限的表现是**静默返回无效结果**（不报错）。

- **选项 A**：接受约束 → 「本地别名库优先 + 严格防抖 + 会话限次 + 缓存」，代价是**首次搜到的新地名可能召回不全**
- **选项 B**：付费买搜索流量包（30 元/万次）或多账号——但**协议 4.9 明确禁止「注册多个账号获取更高配额」**，且一旦付费就落入商业使用，与「个人研究学习目的」冲突 🔴
- **选项 C**：把「实时输入提示」降级为「回车后搜索 + 本地推荐」（`place/text` 一次调用替代逐字多次），代价是**交互体感变差**

> 我的推荐：**A 为主**（这也是唯一合规的选择），但这会直接影响您的交互设计期望 —— 需要您确认「**逐字实时提示**」是否是不可让步的体验要求。

### 问题 3：这次改版的边界是「澳科大通勤」还是「全澳导航」？——这决定了架构投入量级

用户的描述里同时出现了两种口径：「项目现在仅限于澳科大学生 → 做用户与功能的推广 → 升级为全澳门范围内的导航」。

- 如果**仍是「澳科大学生为主」**：可以保留「学校 = 特殊目的地（B/C、N/O、R 三座）」的现有铁律，本地图搜索只覆盖「**任意地点 ↔ 澳科大**」这一个方向 + 少量延伸（口岸），工程量小得多。
- 如果是**「全澳任意 A → 任意 B」**：
  - 候选枚举必须做**通用图搜索**（不再依赖 `commute_plans`）；
  - 「学校不同座 = 不同目的地」这条铁律要泛化为「任意目的地都有多个「入口/侧门」」的通用模型；
  - **必须新做「POI 选择」这一步**（现在只有 6 个地点，之后是任意 POI）；
  - 「我的位置」精度与站台精度的矛盾会从「三座区」扩散到全澳；
  - 运营时间外/郊区/跨境/未开通站点等空状态都要产品化。

> 我的推荐：**分两阶段**。第一阶段做成「**任意地点 → 目的地（含澳科大）**」，但**先限定在高频场景（口岸 / 机场 / 码头 / 赌场 / 高校 / 主要住宅区）**，把「任意 POI」的能力建起来但用白名单收敛质量；第二阶段再放开全量。这样既验证了「全澳导航」的技术路径，又不会一上线就暴露 3.8% 实测覆盖率的短板。
