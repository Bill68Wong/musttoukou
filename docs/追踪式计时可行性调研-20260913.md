# 追踪式计时可行性调研（DSAT 持续监测方案）

> 调研日期：2026-09-13
> 调研人：代码姬（应实测反馈「手动计时太麻烦，能否像录像一样盯着一辆车算站间时长」展开）
> 状态：**只做调研，未写任何生产代码**
> 结论：**技术上可行，且现有基建 90% 已就绪**；但精度受 DSAT 自身的「挂载站更新延迟」硬约束，只能做到 **±(轮询间隔 + 数据更新延迟)** 的粒度，够用于「站间时长统计」，**不够用于秒级判站**。建议先做**一次性验证实验（本地脚本，1~2 小时）**，拿到真实误差分布再决定是否产品化。

---

## 0. 一句话回答

能用「录像式」追踪替代手动计时吗？→ **能，但只能拿到「粗粒度站间时长」，且误差比手动计时大**。

- 手动计时：你按手机的时刻是人类反应延迟（±1~2 秒），但你能**亲眼看到车离站**，且**上下车点是你真正关心的站**。
- 追踪式：机器不知道你关心哪站，只能靠 DSAT 的「挂载站切换」事件推算，而 DSAT 的挂载站**不是实时更新的**（实测：车离站后挂旧站可长达 40 秒+），所以每次「离站时刻」都会带一个 **0~40 秒量级的随机滞后**。

→ **两个「离站时刻」相减时，滞后误差会互相抵消一部分（不是简单相加），但仍在 10~30 秒量级。** 对「1.9 分钟的中位站间时长」来说，这个误差占比 **10~25%**，偏大。

**所以本调研的结论不是「做 / 不做」，而是「值不值得用它替代一部分手动计时」。** 详见第 7 节。

## 1. 用户构想拆解

用户原话：
> 「能不能直接从巴士报站网站上追踪一段时间，来计时……像录像一样，在五分钟内持续监测网站数据，盯着一辆巴士的移动，算他从离开一站到再次离开下一站的时间。」

拆成可验证的工程问题：

| 子问题 | 能否做到 | 关键约束 |
|---|---|---|
| Q1. 能否在 5 分钟内持续监测同一辆车？ | ✅ 能 | 轮询频率 + token 分钟缓存 |
| Q2. 能否识别「车离开 A 站」的时刻？ | ⚠️ 能但有滞后 | DSAT 挂载站更新延迟（实测 0~40s+） |
| Q3. 能否识别「车离开 B 站」的时刻？ | ⚠️ 同上 | 需要先看到车到 B（dwell）再离 B |
| Q4. 两者相减 = 站间时长？ | ⚠️ 数学成立 | 误差 = 两次滞后之差，非零 |
| Q5. 5 分钟内能覆盖几段？ | ⚠️ 通常 3~6 段 | 取决于站间距与停站时长 |

## 2. 现场实测（本次调研新增，非历史数据）

### 2.1 探针设计

新建只读探针 `.verify/poll-probe.mjs`（未入库，gitignored）：
- 复用与生产同款的 **token 签名算法**（`md5(qs)` 插时间，见 `src/lib/dsat/token.ts`）
- 直连 `POST /routestation/bus`，逐帧记录 **每辆车的 `busPlate` / `status` / 挂载站 `staCode` / `idx`**
- 两轮采样：**26 路 8 帧 × 8s**（约 1 分钟）、**25 路 10 帧 × 5s**（45 秒）

> 为什么不直接调 `src/lib/dsat/client.ts`：探针要**不受熔断/记账干扰**地长时间跑，且生产模块的 `purpose` 语义是打点用。实际产品化时**应当且只应当**走 client（见 6.3）。

### 2.2 实测结果一：单次请求极快，轮询无压力

| 轮次 | 线路 | 帧数×间隔 | 单帧延迟 | token 校验 |
|---|---|---|---|---|
| 1 | 26 | 8 × 8s | **26~81 ms** | 全 000（正常） |
| 2 | 25 | 10 × 5s | **28~61 ms** | 全 000（正常） |

→ **单帧 ~30ms**，比之前估的「200ms 往返」还快（那是 Vercel→Supabase 的库往返，不是 DSAT）。**DSAT 侧本身完全承受得起 5 秒一次的轮询**。

### 2.3 ★ 实测结果二：挂载站跳变确实存在，且能捕捉到

25 路 5s 间隔 45 秒窗口，**抓到 5 辆车发生状态跳变**：

| 车牌 | 序列（45 秒内） | 跳变含义 |
|---|---|---|
| AB5413 | `s0@C656` → ... → **`s1@C654/3`** | 到达下一站（离 C656 后 15s 检测到停在 C654/3） |
| AB4969 | **`s1@C653` → `s0@C653`** | **离开 C653**（dwell 结束后出发） |
| AB4741 | **`s1@M172/16 → s0@M172/16`** | 离开 M172/16 |
| AB5340 | **`s1@M14 → s0@M14`** | 离开 M14 |
| AA7854(26路) | `s0@M16/1` → **`s1@M109`** | 到达下一站 |
| MX7769(26路) | `s0@T360` → **`s1@T376/1`** | 到达下一站（跨了 T373，见 3.2） |
| AC4145(26路) | `s1@T380 → s0@T380 → s1@T379 → s0@T379` | **完整「离 T380 → 到 T379 → 离 T379」** ✅ |

**AC4145 的序列正是用户要的东西** —— 一次「离 A → 到 B → 离 B」被完整捕捉，说明**方案在原理上成立**。

### 2.4 ★ 实测结果三：停站（dwell）时长极不稳定，是误差主源

25 路 45 秒窗口里，**15 辆车中 12 辆全程 `status` 与挂载站不变**：
- `AB5479` **连续 10 帧（45 秒）`s1@T363/2`** —— 停站超过 45 秒
- `AB5833` 连续 10 帧 `s1@M91`、`AB4580`/`AB5503` 连续 10 帧 `s1@M1/13`
- 而 `AB5413` 只在 C654/3 停了 **35 秒**（帧4~帧10 都是 s1）

→ **停站时长从几秒到 45 秒+ 不等**。这意味着「离开 A 站」的时刻**不能靠 A 站本身的到达时间推算**，必须真的捕捉到 `s1@A → s0@A`（或 `s?@A → s1@B`）那次跳变。

## 3. 三个硬约束（决定精度上限）

### 3.0 ★ 附加实证：官网自己就是「10 秒自动刷新」（回答用户观察）

用户观察：「我自己在看 DSAT 网页时，我没点刷新，它有时候会自己刷新到下一站，为什么？」

**答案：这是 DSAT 官网前端自己的循环轮询，间隔 10 秒。** 证据（本次实测抓取官网前端 JS
`/macauweb/static/assets/js/index.6e5a0476.js`，142KB）：

```js
// 唯一与数据刷新相关的定时器（其余 setInterval 只有 Bootstrap 走马灯）
h.a.getBusFrequency(e, o, function (n) {
  p.a.showLoading(false);
  if (n.code === "1") {
    Mt(n.data);                        // 渲染数据
    q = setTimeout(function () { t(e); }, 1e4);   // ★ 1e4 = 10000ms → 重新调度自己
  } else Mt([]);
});
```

- `1e4` = **10000 毫秒 = 10 秒**；这是**递归自调度**（`clearTimeout(q)` 后重设），不是 `setInterval`
- 每次成功返回后 10 秒再问一次 → 所以你不点刷新，页面也会自己跳到下一站
- 全 JS 只此一处与「轮询」有关（另有 `,1e3` = 1 秒，是**搜索输入防抖**；`interval:5e3` 是 Bootstrap 轮播）
- `timeout: 1e4` / `15e3` 是请求超时，不是刷新间隔

**结论**：官网前端轮询间隔 = **10 秒**，与官方「巴士定位数据 10 秒更新」的说法一致。

→ **对追踪式方案的意义**：
1. **10 秒就是官方自己认为的「够用频率」** —— 我们轮询到 5 秒已经比官方更密，**再密无意义**（数据源本身只有 10 秒粒度）
2. 这也**印证了第 4 节的精度结论**：官网 10 秒刷新下你仍会看到「挂着不动 / 突然跳站」，正是因为 DSAT 服务端数据本身就是这个粒度
3. **我们复刻官方频率（10 秒）即可，无需更快**；若实验想更保守可 10~15 秒，降低风控与无谓请求

### 3.1 🚨 约束一：挂载站更新延迟（最大误差源）

历史实证（`docs/站距调研-20260904.md` §v0.8.4）：
> `probe-switch.ts` 26 路 20s×5 帧：**AB5503 `s0@C652` 连续 40s+ 后才直接 `s1@C655`**

本次实测再次印证：25 路 `AB5479` 在 T363/2 **连挂 45 秒不变**。

**机理**：DSAT 的挂载站按「到站事件」更新 —— 车离站后**仍挂旧站（status 变 0）**，直到驶到下一站停稳才切到新站。所以：
- 「离开 A 站」的时刻 ≈ DSAT 把该车标记为 `s0@A` 的那一帧 → **真实离站时刻与检测时刻之间隔着「轮询间隔」**
- 但更糟的是：**DSAT 自身何时把 `s1@A` 改成 `s0@A` 也不确定**（官方定位数据号称 10 秒更新，但挂载站切换逻辑是「到站驱动」而非「定时驱动」）

→ **单次离站检测的误差 = 轮询间隔 + DSAT 内部更新延迟**，后者可能 0~40 秒。

### 3.2 🚨 约束二：可能「跳站」（漏掉中间站）

本次实测抓到 **MX7769（26 路）：`s0@T360`(idx47) → `s1@T376/1`(idx48)**。

按 `docs/站距调研-20260904.md` 的 26 路站序，T360 与 T376/1 **序数相邻**，看似没问题。但 AA7854 的 `s0@M16/1`(idx3) → `s1@M109`(idx4) 也相邻。**本次两轮探针未抓到真正的跳站**，但历史文档记录过「甩站」（`station_pass`/`station_skip` 事件类型存在），说明**巴士甩站是真实存在的**。

→ 若一辆车在 A、B 之间甩过了 C，那么「离 A → 离 B」的时长**包含了一个未停站的区间**，与「A→C→B 两段之和」不能等同。**追踪式计时无法区分「停站」与「甩站」，除非 DSAT 的挂载站跳变能暴露它（跳 2 个 idx 就是甩站，但本次未观测到）。**

### 3.3 🚨 约束三：token 分钟级缓存 → 频率有下限也有上限

`genToken` 的时间戳精确到**分钟**（`YYYYMMDDHHmm`）。同一分钟内 token 不变 → **同一分钟内可复用**（省 md5）。但**跨分钟必须重新生成**。

→ 对 5 秒轮询无影响（每分钟最多 12 次，token 换 1 次）。**但要注意：5 分钟内会跨 5 个分钟边界，每次都要重算 token**——探针实测全 000，未遇到 1200。

## 4. 精度量化（核心结论）

设：轮询间隔 = `P`，DSAT 挂载站切换延迟 = `D`（随机，实测 0~40s）。

- 单次「离站时刻」检测误差 ≈ `[0, P + D]`，中位约 `P/2 + D/2`
- 「离 A」与「离 B」两次相减 → 误差 ≈ 两次滞后之差（**部分抵消**，非相加）

**代入实测**：若 `P = 5s`、`D` 中位 15s：
- 单次偏差 ~10s 量级
- 相减后偏差 ~ **±10~15 秒**
- 对中位站间时长 1.9 分（114 秒）→ **相对误差 ~10~13%**

**对照手动计时**：你的手机秒表误差 ±1~2 秒，但你可能**看错车/看错站**（尤其多线共站）；追踪式的 ±15 秒是**机械误差**，无「看错」风险。

| 指标 | 手动计时 | 追踪式（P=5s） |
|---|---|---|
| 理论精度 | ±1~2s | ±10~15s |
| 系统误差 | 看错车/站（偶发大错） | 无 |
| 覆盖范围 | 仅你实际乘坐 | 全澳任意线路 |
| 人力成本 | 每趟都要动手 | 挂机即可 |
| 样本量 | 1 趟 = 1 套 | 1 趟 = 1 套（同） |

→ **追踪式的价值不在「更准」，而在「不用人动手 + 能覆盖你不坐的线路」。**

## 5. 5 分钟能采几段？（回答 Q5）

从 25 路实测反推：45 秒窗口内，一辆正常行驶的车（`AB5413`）走完 **1 段**（C656→C654/3）并开始 dwell。

- **平均每段耗时 ≈ 站间行驶 + 停站 ≈ 1.9 + 0.5~0.7 分钟 ≈ 2.5~3 分钟**
- **5 分钟窗口 ≈ 能覆盖 2~3 个完整站段**

> ⚠️ 但要注意：若你要测的是「**上车前 N 站**」的时段，5 分钟往往**不够**（N 站可能要 10~15 分钟）。建议把窗口从 5 分钟提到 **10~15 分钟**，或**按需长跑**。

## 6. 采集侧设计（若要做）

### 6.1 复用现有基建（90% 已就绪）

| 能力 | 现成位置 | 状态 |
|---|---|---|
| token 签名 | `src/lib/dsat/token.ts` | ✅ 已实现 |
| 统一请求（超时/熔断/记账） | `src/lib/dsat/client.ts` `dsatPost` | ✅ 已实现 |
| 轮询语义预留 | `src/config/risk.ts` `poll: { enabled: false, intervalSec: 60 }` | ⚠️ **已预留未启用** |
| purpose 类型 | `client.ts` `DsatPurpose = "timer_grab" \| "poll" \| "sync"` | ✅ **`"poll"` 已存在** |
| 记账表 | `dsat_call_logs` | ✅ 已实现 |
| 快照表 | `bus_snapshots`（含 `polled_at`/`status`/`stops_away`） | ✅ 已实现，**可复用存放逐帧数据** |

→ **不需要新建底层，只需写一个「循环调用 + 状态机」的上层。**

### 6.2 去哪跑？（本地 vs Vercel）

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 本地脚本**（推荐做实验） | 零部署、零成本、可长跑、可调试 | 需开着电脑；澳门本地 IP 直连 DSAT ~30ms |
| **B. Vercel Cron**（不建议） | 自动 | 函数最长 60s（`maxDuration`）→ **跑不了 5 分钟连续轮询**；且 Serverless 无常驻进程 |
| **C. Vercel + 外部 cron 打点** | 可绕过 60s | 复杂度高，且每帧一次冷启动 |

→ **实验阶段用 A（本地）；若产品化，需 B/C 之外的方案（如本地常驻 + 定期上云），这是一个「架构拐点」，需单独拍板。**

### 6.3 状态机设计（核心逻辑）

```
对目标车牌 P 持续轮询，维护 prev = { status, idx, ts }：
  每帧 new = 找到 P 的 (status, idx, ts)
  若 new.status == '1' 且 prev.status == '0' 且 new.idx != prev.idx:
      → 事件「到达 new.idx」，记录 arrive_ts
  若 new.status == '0' 且 prev.status == '1' 且 new.idx == prev.idx:
      → 事件「离开 prev.idx」，记录 depart_ts
      → 若上一事件是「到达 prev.idx」，则 segment = depart_ts(prev) - 上一个 depart_ts
```

⚠️ **关键细节**：用户要的「离开 A → 离开 B」= **两次 `s1→s0`（同 idx）**。中间的「到达 B」是必要的**证据帧**（证明车确实停在 B 而非甩过）。若从未观察到 `s1@B`，则该段**不可用**（可能是甩站，或轮询太慢错过 dwell）。

→ **必须保存「每帧原始数据」，事后再跑状态机**（别边采边判——判错了无法回溯）。这也是为什么建议先写**实验脚本**而不是直接产品化。

## 7. 与手动计时的对比与取舍（最重要的判断）

### 7.1 追踪式**能**解决的
- ✅ 你不用再掏手机按秒表
- ✅ 能采**你不坐的线路**（例如想覆盖 51B/25AX 但你不常坐）
- ✅ 能产出**逐站时刻序列**（比手动打点更细）

### 7.2 追踪式**不能**解决的
- ❌ **精度不如手动**（±10~15s vs ±1~2s）
- ❌ **不知道「你在哪站上下车」**——它记的是全车行程，不是你的通勤段
- ❌ **无法覆盖步行段**（`walk_times` 仍需手动方案；追踪只管乘车段）
- ❌ **无法区分停站/甩站**，除非跳 idx

### 7.3 关键洞察：它与现有 `segment_stats` 的口径**不完全兼容**

现有 `segment_stats` 的 `arrive_kind` 分 `stop`（起点停靠，含停站）/ `pass`（起点甩站，纯行驶）。**追踪式的「离 A → 离 B」天然是 `stop` 口径**（因为它要求观察到 dwell），**无法产出 `pass` 口径样本**。

→ **追踪式的样本可以直接并入 `segment_stats`，口径记为 `arrive_kind='stop'`**（与手动打点的「停靠」样本同源），**但不能替代 `pass` 样本**。

## 8. 风险与合规

| 风险 | 等级 | 说明 |
|---|---|---|
| 官方接口变更 | 中 | 逆向接口无 SLA；已有熔断兜底 |
| 请求频率 | 低 | 5s × 单线路 = 12 次/分钟，单线路量级极小 |
| 合规 | 低（自用） | 官方办法「巴士定位数据依申请开放且尚未开放、个人不可申请」；本方案是**服务端自用轮询**，非对外提供数据服务，风险低。**若将来对外开放则需重新评估** |
| 被封 IP | 低 | 澳门本地 IP；单线路低频；`dsat_call_logs` 可监控异常 |
| 数据污染 | **中** | 若把追踪结果写进生产库，须有**来源标记**，避免与手动样本混淆 |

**必须遵守**（沿用项目铁律）：
- 非公开接口**禁止前端直连**，一律服务端
- 追踪数据入 `bus_snapshots` 时**必须带 purpose/source 标记**
- 线上验证**一律只读**

## 9. 结论与建议

### 9.1 可行性判定
**可行**。原理已由实测验证（AC4145 完整捕捉「离 A → 到 B → 离 B」），基建 90% 现成，合规风险低。

### 9.2 但有一个「诚实的天花板」
**追踪式的精度上限由 DSAT 自身的挂载站更新延迟决定，无法通过提高轮询频率突破。** 提到 1 秒一次也只能把误差从 ±15s 压到 ±12s 左右（因为瓶颈是 DSAT 内部延迟 `D`，不是你的轮询间隔 `P`）。

→ **它不能替代手动计时，只能作为「补充覆盖」手段。**

### 9.3 建议路径（三选一，见文末选择题）

**方案① 一次性验证实验（推荐）**
- 写一个本地脚本，对 1~2 条你关心的线路长跑 15 分钟，采集逐帧原始数据
- 用「手动计时已知的一段」做对照，量化真实误差分布
- **产出：一份误差报告 + 是否值得产品化的判断**
- 成本：约 1~2 小时，**零生产代码改动**

**方案② 直接产品化**
- 启用 `RISK.poll`，写轮询服务，结果入库
- ⚠️ 需要解决「Vercel 跑不了长任务」的架构问题，成本高，且精度可能令你失望

**方案③ 先不做**
- 继续手动计时 + 按 `docs/采集清单-v3-2026-09-13.md` 跑真缺段
- 追踪式**作为独立的下一步**，等建模（#5）真正需要「大量站间样本」时再启动
